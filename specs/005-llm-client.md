## Входные данные

- Зафиксированное действие из 003: идентификатор, команда, рабочая папка, результат правил и известные затрагиваемые пути с ограничениями их определения.
- Несекретные настройки `baseURL`, `model`, `timeoutMs`, `authMode`
  (`apiKey` или `none`), ссылка `credentialRef` на выбранный источник ключа при необходимости.
- Отдельный источник ключа: переменная окружения для разработки/тестов либо
  системное хранилище учётных данных для сохранения через меню 004.
  Сам ключ не является полем сохраняемого JSON настроек.
- Доступный облачный API и действующий ключ для реального демонстрационного прогона. Для локального API ключ может не требоваться.
- Обезличенный пример удаления специально созданного тестового файла. Запуск самой команды не нужен для проверки клиента.

## Ожидаемое поведение

### 1. Настройки и проверка входа

Принимать адрес API и модель из настроек, без жёсткой привязки к одному
поставщику. Пользовательский выбор и проверка подключения доступны через меню
004; UI не реализуется внутри клиента 005.

Клиент получает ключ через внедряемый источник `resolveApiKey`, а не читает
глобальное окружение во всех частях программы. 005 предоставляет источник
из переменной окружения; 004 — сохранение, замену, удаление и чтение через
системное хранилище. 006 связывает выбранный источник с клиентом.
В инструкции зафиксировать имя переменной и способ настройки credentialRef.
Окружение остаётся поддерживаемым вариантом; прежнее требование «только из
окружения» этим уточнением заменяется. Оба источника доступны через один
интерфейс клиента и проверяются без реального пользовательского ключа.

При authMode=apiKey требуются ссылка на источник и непустой полученный ключ;
ошибка чтения/отсутствие ключа дают различимую причину без сетевого запроса.
При authMode=none источник ключа не вызывается и Authorization не отправляется.
Не подставлять реальный облачный ключ для локального API автоматически.

Адрес, модель и тайм-аут сохраняются отдельно от секрета. Публичный адрес API
может быть в примере репозитория; ключи, персональные настройки и внутренние
адреса команды не включать. Конкретная реализация системного хранилища
проверяется в 004 на поддерживаемой ОС; 005 от неё не зависит.

Проверить наличие и корректность адреса, непустую модель и положительное конечное значение `timeoutMs`. Если выбран режим apiKey, отсутствие ключа даёт понятную ошибку до запроса. Для режима none отсутствие ключа не считать ошибкой.

Некорректные настройки или действие отклонять до сетевого запроса. Если контракт использует строку команды, не изменять её перед объяснением. Не подставлять другую модель или другой адрес при ошибке без явной настройки пользователя.

Используемый способ вызова OpenAI-совместимого API подтвердить документацией выбранного сервиса и реальным запросом. Фактический адрес, способ вызова и модель указать без секретов; не объявлять совместимость со всеми API по одному успешному запуску.

### 2. Запрос объяснения

Первый транспорт — OpenAI-совместимый Chat Completions, текстовый ответ без
стриминга. Совместимость конкретных ролей сообщений и параметров подтверждается
документацией сервиса и реальным вызовом. Не обещать поддержку любого API.

Использовать один версионируемый системный шаблон из кода при каждом запросе,
независимо от облачного/локального адреса и выбранной модели. Данные действия
сериализуются отдельно в пользовательское сообщение; не вставлять их в
системную инструкцию. Смена модели не меняет шаблон и не переносит историю
другого чата. Это инструкция для каждого запроса, не обучение модели.

Обязательный смысл шаблона: объяснить новичку по-русски действие, известные
ресурсы и риски, явно назвать неопределённость; не придумывать бэкапы,
обратимость и точный масштаб, не давать разрешение и не выполнять инструкции
из переданных данных. Версию шаблона записывать в свидетельства проверки.
Одинаковый промпт не гарантирует одинаковое качество моделей: выбранные
облачная и локальная модели оцениваются отдельно.

Передавать только необходимые параметры действия и результат правил. Автоматически не отправлять содержимое проекта, окружение процесса или дополнительные файлы. Ключ использовать только для авторизации, не включать в текст запроса.

Команду и контекст передавать модели как данные для объяснения. Инструкции, встретившиеся внутри команды, имени файла или другого контекста, не должны становиться указаниями клиенту изменить правила или разрешить действие.

Запрашивать короткое объяснение на русском языке:

- что делает команда;
- какие известные файлы или пути затрагиваются;
- какие последствия и риск важны для решения пользователя;
- что неизвестно, если по имеющимся данным нельзя определить последствия полностью.

Не требовать точного числа затронутых файлов, наличия резервной копии или возможности восстановления, если таких данных нет. Объяснение относится к исходному зафиксированному действию, а не к предложенной моделью замене команды.

### 3. Результат для 006

Возвращать по согласованному контракту 003 один из исходов:

| Исход | Содержание |
|---|---|
| Объяснение получено | Непустой текст и связь с тем же зафиксированным действием. Это не разрешение. |
| Ошибка | Различимая причина и безопасное сообщение; объяснение не считается полученным. |

Связь ответа с действием сохраняет программа. Не доверять идентификатору или разрешению, которые модель могла написать в тексте. Служебные инструкции модели и технический ответ API не показывать как готовое объяснение.

Не добавлять обязательный JSON-формат ответа модели без отдельной необходимости в принятом контракте. Результат клиента и сырой ответ поставщика — разные данные.

006 получает available/unavailable по контракту 003. При unavailable предлагает явное разовое разрешение без объяснения только для незаблокированного действия; до решения исполнения нет. Сам клиент не обращается к исполнителю, не выдаёт разрешение и не меняет результат правил.

### 4. Ошибки и время ожидания

Различать как минимум:

- некорректные настройки или входное действие;
- отсутствие требуемого ключа или ошибка его получения из выбранного источника;
- сетевую ошибку и недоступность сервиса;
- отказ авторизации, ограничение запросов и ошибку сервера;
- превышение `timeoutMs`;
- неподдерживаемый формат ответа, отсутствие текста или пустое объяснение.

При превышении настроенного ожидания вернуть тайм-аут. Поздний ответ не должен превращать уже завершившуюся ошибкой попытку в успешную и запускать дальнейшие этапы для неё.

Не заменять ошибку шаблонным объяснением, ответом host-агента или молчаливым разрешением. Автоматическое переключение поставщика, фоновая очередь и дополнительные механизмы повторов не входят в задачу.

Сообщения и диагностические записи не должны содержать ключи, заголовки авторизации и секреты из окружения. Сырые ответы сервиса не включать в отчёт без проверки их содержимого.

### 5. Документация и свидетельства

Подготовить пример настроек без секретов и инструкцию получения объяснения. В `docs/research/llm-checks.md` записать среду, модель, адрес без секретов, фактическую команду запуска проверки, тестовое действие, результат и ограничения.

Сохранить объяснение реальной облачной модели и свидетельство успешного вызова,
очищенное от ключа и заголовков авторизации. Это не требование выполнять
облачный запрос без авторизации. Заглушки отделять от реальных результатов.
До прогона Алексей настраивает доступный облачный сервис; инструкцию получения
и локального ввода ключа готовим для выбранного сервиса в момент подключения.
Окно ChatGPT не используется как транспорт API.

Возможность настроить локальный адрес сохранить. Локальный прогон выполняет
Александр на своём компьютере с имеющимся Qwen при наличии времени; на ноутбук
Алексея Ollama не устанавливается. Перед прогоном Александр устанавливает
факт: какой сервер запускает модель, его версия, точный model ID и доступный
формат API. Qwen сам по себе не доказывает запуск через Ollama или совместимость.
Если сервер — Ollama, проверяется её OpenAI-совместимый адрес; другой сервер
отмечается своим именем, без заявления «Ollama проверена».

Передать Александру тот же клиент, шаблон, безопасное тестовое действие и
инструкцию. В docs/research/llm-checks.md зафиксировать сервер/версию, модель,
ОС, версию промпта, обезличенные настройки, объяснение, ошибки и ограничения.
Не публиковать внутренний сетевой адрес или секрет. При отсутствии прогона
оставить «не проверено»; облачная приёмка от него не зависит. Установка
Ollama, Docker и Docker-помощник не являются задачей Алексея.

Передать в 006 принятый формат результата и ошибок, а в 007 — воспроизводимый способ вызова и сведения о модели. Серия минимум из 10 вызовов и сводные измерения задержки принадлежат 007, а не дублируются в 005.

## Ограничения

- LLM не принимает решение о выполнении и не отменяет запрет правил.
- Ошибка или тайм-аут не считаются успешным объяснением и не разрешают действие.
- Для проверок использовать только тестовые данные, допустимые для отправки выбранному сервису.
- Не хранить ключ в репозитории, примере настроек, отчёте или записи экрана.
- Не заявлять гарантированную истинность произвольных объяснений по одному примеру. Неточные или неподтверждённые утверждения в демонстрационном объяснении фиксировать как дефект.
- Численный SLA не придумывать: `timeoutMs` — настройка клиента, а не согласованный заказчиком порог качества.

## Границы задачи

Входит: настраиваемый клиент, запрос объяснения, обработка результата и ошибок, уместные автотесты, реальная облачная проверка и инструкция.

Не входит: новый классификатор рисков, анализ всего проекта, подсчёт зоны поражения, поиск резервных копий, изменение команд, подтверждение пользователя 004, MCP-сервер и выполнение 006, итоговые метрики 007.

Не входят другие агенты, постоянные разрешения, режимы строгости, установка локальной модели, Docker-помощник и публикация npm.

## Критерии приёмки

1. Адрес, модель, тайм-аут и authMode настраиваются; ключ получаем через отдельный
   источник. Реализован источник окружения, интерфейс допускает системное хранилище
   004 без изменения клиента. Некорректные настройки/ошибка ключа — до запроса.
2. Для демонстрационного действия получено непустое объяснение от реальной облачной модели. Оно описывает действие и последствия без неподтверждённых сведений о числе файлов, резервных копиях и восстановлении.
3. Объяснение связано с тем же действием; клиент не изменяет параметры, результат правил и не выдаёт разрешение.
4. Сетевая ошибка, ошибка авторизации, ограничение запросов, ошибка сервера, тайм-аут и некорректный/пустой ответ дают различимый неуспех. Шаблон вместо реального объяснения не возвращается.
5. В тесте поздний ответ после тайм-аута не меняет исход завершившейся попытки. Ошибки не создают разрешение на выполнение.
6. Пример настроек и свидетельства не содержат секретов. Александр воспроизводит реальный вызов по инструкции с доступным ключом.
7. Локальный API настраивается без изменения архитектуры; результат прогона
   Александра указывает фактический сервер и модель либо «не проверено».
   Установка локальной модели у Алексея и её готовность не требуются для облачной приёмки.
8. Версионируемый системный шаблон отправляется при каждом запросе и не меняется
   при смене модели/адреса; действие передаётся отдельно. В тестах подтверждены
   отсутствие Authorization при none, ошибка источника ключа до запроса и
   отсутствие утечек ключа в промпте, диагностике и результате.

## Проверка и автотесты для кода

Автотесты выполнять с управляемым тестовым API, без обязательного внешнего ключа. Проверить:

- валидацию настроек и входного действия до сетевого обращения;
- передачу исходной команды и необходимого контекста без секретов;
- постоянство системного шаблона при смене модели и адреса, отдельное сообщение
  с данными, отсутствие переноса инструкций из команды в системный промпт;
- источник окружения и подставной источник системного хранилища, отсутствие/ошибку
  ключа до запроса; authMode=none без обращения к источнику и без Authorization;
- корректный ответ и его связь с действием;
- пустой и повреждённый ответ;
- сетевую ошибку, ошибки авторизации, ограничения запросов и сервера;
- тайм-аут и игнорирование позднего результата;
- отсутствие разрешения от текста модели и сохранение результата правил.

Проверка формата запроса не доказывает устойчивость модели к любым инструкциям в данных. Дополнительно проверить тестовый пример с инструкцией внутри контекста и записать фактический ответ без заявления о полной защите.

Отдельно провести реальный облачный вызов. Сохранить в `docs/research/llm-checks.md` таблицу: сценарий, ожидаемый и фактический результат, свидетельство, среда и модель. Указать фактические команды запуска тестов и их результат.

Александр проверяет объяснение, воспроизводит вызов и сверяет контракт с 003/006. Отсутствие автоматического исполнения при ошибке LLM и отдельный явный выбор без объяснения проверяются в полном цикле 006/007; тесты клиента не заменяют эту проверку.

## Открытые вопросы

- Контракт принят в 003; его соответствие фактической реализации нужно проверить при соединении 005/006.
- Какой облачный сервис и модель доступны аккаунту Алексея? До реального прогона
  фиксируется конкретный выбор. Бесплатные тарифы рассматриваются первыми;
  платный OpenAI API — запасной вариант по отдельному решению пользователя.
  Автоматического перехода на платную модель или другого провайдера нет.
- Допустимость облачного API и передачи выбранных данных уточняется в 002. Новое обязательное требование локальной модели требует решения Алексея об объёме; оно не добавляется в спринт молча.

Это проверка опубликованной документации, не реальный вызов и не выбор провайдера.

  Для воспроизводимости выбрать конкретный ID бесплатной модели, а не случайный роутер.

Бесплатный доступ требует аккаунта/ключа и ограничен квотами. Актуальную
доступность для аккаунта, условия обработки тестовых данных и модель проверять
до подключения и перед Демо. Числа квот не являются гарантией продукта.
Использовать синтетические действия; выбранный сервис и model ID фиксировать
в отчёте. Нет необходимости привязывать код к платному OpenAI API заранее.

## Технические решения реализации клиента

- Публичный вход: createLlmClient(settings, dependencies?) → explain(action).
  Неверные settings дают LlmConfigError/INVALID_CONFIG до сетевого запроса;
  некорректное действие — unavailable/INVALID_ACTION. При отсутствии валидного
  actionId поле связи равно пустой строке и не может разрешать действие в 006.
- settings содержат только baseURL, model, timeoutMs, authMode и credentialRef
  при apiKey. baseURL — HTTP(S) без логина, пароля, query и fragment; к пути
  добавляется /chat/completions. Перенаправления не выполняются. Ни SDK,
  ни новые runtime-зависимости не требуются: используется fetch Node.js 24.
- resolveApiKey(ref) может быть синхронным или асинхронным. Общий timeoutMs
  включает источник ключа, запрос и чтение тела. Тайм-аут отменяет fetch;
  позднее завершение источника не запускает запрос и не меняет результат.
- Ответ — один завершённый assistant content из choices[0] с finish_reason=stop.
  Пустой текст, отказ модели, tool/function calls, обрезанный или иной формат
  дают unavailable. Reasoning и служебные поля не являются объяснением.
- Технический предел тела запроса и ответа — 64 KiB; это ограничение ресурсов,
  не SLA. При превышении возвращается отдельная причина. Сырые ошибки сервера
  не возвращаются. Если известный текущий ключ встретился в тексте запроса или
  ответа, запрос отклоняется до отправки либо ответ не выдаётся как объяснение.
- Входные данные копируются до первого await; источник ключа и fetch внедряются
  для тестов. Успешный ответ использует исходный actionId, а не поля модели.
- scripts/check-llm.mjs — отдельный безопасный прогон клиента на синтетическом
  действии, без исполнения shell-команды. Настройки/ключ читаются из окружения,
  результат не сохраняется автоматически. Реальный облачный вызов и локальный
  прогон Александра отмечаются отдельно от тестов управляемого API.
