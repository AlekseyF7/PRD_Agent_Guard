Одна точная команда удаления больше не ограничивает поддерживаемый вход.
Это решение команды; оно не утверждает выполнение всех целей PRD.

## Ожидаемое поведение и контракт

### 1. Вход действия

MCP-инструмент принимает объект ровно с двумя собственными полями:

```json
{"command": "rm -- sample.txt", "cwd": "/absolute/path/to/test-project"}
```

Это пример, не существующая тестовая папка. Проверка JSON выполняется во
время исполнения: массивы, null, лишние или отсутствующие поля, неверные типы
отклоняются. `command` — непустая, не только пробельная строка, без NUL;
её не обрезают и не переписывают. `cwd` — существующая абсолютная папка,
приводимая через realpath к каноническому пути. Путь к файлу, относительный
или недоступный путь отклоняются. Поля `approved`, `user_approved`, `actionId`,
политики и корень рабочей области не принимаются от агента.

### 2. Настройки ядра

Приложение передаёт отдельно проверяемый объект настроек:

```json
{
  "workspaceRoot": "/absolute/path/to/test-project",
  "mode": "paranoid",
  "policies": {
    "file_delete": "ask",
    "git_destructive": "ask",
    "git_force_push": "ask",
    "outside_workspace": "block"
  }
}
```

`workspaceRoot` — существующая абсолютная папка, канонизируется через realpath;
не угадывается из текущей папки процесса. В первом объёме допустим только
`paranoid`, значения политик — `ask` или `block`; неизвестные ключи/значения
дают `INVALID_CONFIG`. Пример задаёт начальные значения меню. Настройки
не являются аргументами инструмента действия. Их выбор и сохранение в JSON
через меню — 004, загрузка приложением — 006, схема и проверка — 003.

Для проверки вхождения пути используются границы каталогов, не совпадение
строкового префикса: соседняя папка `project-copy` не входит в `project`.
Символические ссылки учитываются через канонизацию. Политика выхода действует
для cwd и статически определимых целей операций с файлами. Неопределимые
цели не объявляются внутренними. Это ограниченный анализ, не OS-песочница.

Некорректная настройка не создаёт рабочий экземпляр ядра. Изменение настроек
отменяет ожидающие решения и требует нового цикла проверки; оркестрация 006
применяет настройки атомарно, не переиспользует старое согласие. Агент не
может менять политики через поля запроса. Корпоративная неизменяемость
настроек в этот объём не входит.

### 3. Правила и решение

Порядок: валидация → анализ правил → применение политик → снимок результата.
Каждое правило имеет стабильный `ruleId`, категорию политики, причину риска
и явно описанную область распознавания. Новое правило добавляется без
переписывания остальных правил и интеграционных слоёв.

| Категория | Первый набор распознаваемых операций |
|---|---|
| `file_delete` | Прямой вызов `rm`, в том числе с флагами и литеральными путями |
| `git_destructive` | Прямые `git reset --hard` и удаляющие формы `git clean -f`, включая `-fd`/`-fdx` |
| `git_force_push` | Прямой `git push` с `--force`, `-f` или `--force-with-lease` |
| `outside_workspace` | Канонический cwd или известная цель файловой операции вне workspaceRoot |

Поддерживаемые формы, флаги и ограничения каждого правила записываются
рядом с реализацией и проверяются тестами. Нельзя искать `rm` простым
подстрочным совпадением: `echo 'rm sample.txt'` не является удалением.
Обёртки, подстановки, составные команды, динамические пути и неизвестные формы
помечаются как неполный/неизвестный анализ. Их нельзя объявлять безопасными
или обещать полное распознавание shell. Если в анализе уже найден запрет,
неполнота остальных частей его не отменяет. При отсутствии обнаруженного
запрета неизвестная корректная команда получает `ask`.

| Решение | Условие и дальнейшее поведение |
|---|---|
| `block` | Некорректный запрос либо сработавшее правило с политикой block. Причина показывается сразу, без LLM и кнопки разрешения. |
| `ask` | Корректное незаблокированное действие. В Paranoid это все такие команды, включая `ls` и команды без совпадений правил. |
| `allow` | Зарезервировано для будущего Fast; первая реализация не возвращает его. |

При нескольких совпадениях любой `block` имеет приоритет. Отключение
автоблокировки категории означает `ask`, не `allow`. Риск и автоматический
запрет — разные понятия. LLM не меняет решение правил. Политики распознают
только заявленные формы: неизвестная команда с ask не доказывает отсутствие
внутри неё запрещённой операции. Это ограничение должно быть видно пользователю.

### 4. Неизменяемое действие и ответ

Для корректного действия ядро создаёт новый UUID `actionId`, копирует значения
и делает весь снимок неизменяемым, включая вложенные массивы/объекты:

```json
{
  "decision": "ask",
  "action": {
    "actionId": "<generated-uuid>",
    "operation": "execute_command",
    "command": "rm -- sample.txt",
    "cwd": "/absolute/canonical/test-project",
    "affectedPaths": ["/absolute/canonical/test-project/sample.txt"],
    "analysis": "partial",
    "risks": [{"ruleId": "shell.rm", "category": "file_delete", "reason": "Удаление файла"}]
  },
  "reason": "Требуется решение пользователя"
}
```

`analysis`: `recognized` — форма разобрана в заявленных границах,
`partial` — определена только часть последствий, `unknown` — надёжных сведений нет.
Это не оценка безопасности. `affectedPaths` содержит только определимые цели,
а не полный список последствий. Наличие файла, бэкапа и обратимость не утверждаются.
Для корректного заблокированного действия возвращаются тот же снимок,
`decision: block`, `code: POLICY_BLOCK` и причина запрета.
Для некорректного входа — `decision: block`, `code`, `reason`, без `action`.

Коды ошибок валидации: `INVALID_REQUEST`, `INVALID_COMMAND`, `INVALID_CWD`.
`INVALID_CONFIG` — ошибка создания/обновления настроек, не разрешение обработать
запрос с другими настройками. Не возвращать окружение, секреты и сырые системные ошибки.

UUID не является разрешением. Повторный вызов получает новый UUID даже при
тех же аргументах. Изменение входного объекта не меняет снимок. Изменённые
command/cwd требуют новой проверки, объяснения и решения пользователя.
Снимок не замораживает файловую систему; гонки и проверка состояния перед
исполнением относятся к 006, а не считаются решёнными копированием аргументов.

### 5. Границы 004/005/006

Общие оболочки данных (программные интерфейсы реализуются в соответствующих задачах):

```text
005: action -> { actionId, status: available, text: <непустое объяснение> }
             | { actionId, status: unavailable, error: { code, message } }
004: { action, explanation } -> { actionId, outcome }
     outcome: allow_once | allow_once_without_explanation | deny | cancel | no_answer | error
006: соединяет этапы, проверяет источник и состояние решения, выполняет один раз
```

При `block` 006 не вызывает 005/подтверждение/исполнитель. При `ask` сначала
ожидает результат LLM. Для available показывает «Разрешить один раз»/«Отказать»;
для unavailable — предупреждение и «Разрешить один раз без объяснения»/«Отказать».
Без статической подсказки этот второй вариант также доступен. Ошибка LLM
сама ничего не разрешает. Пока ответ ещё ожидается, состояние — ожидание,
а не unavailable. Пустой/некорректный ответ, ошибка и тайм-аут — unavailable.

006 принимает allow_once только при available, allow_once_without_explanation
только при unavailable; остальные исходы не запускают команду. Поздний ответ
LLM не меняет уже показанное состояние и согласие. Ответ принимается только
для ожидающего действия через проверенный доверенный канал. Совпадение UUID,
текст агента и JSON с разрешением этого не доказывают. Ошибка/закрытие канала
и отсутствие человеческого ответа не превращаются в согласие.

## Границы задачи

Входит: контракт, runtime-валидация входа и настроек, реестр нескольких правил,
политики block/ask, неизменяемые снимки, интерфейсы данных и автотесты ядра.
Код — TypeScript согласно PRD; конкретные средства сборки и тестов фиксируются
при реализации. Ядро не вызывает LLM, UI, MCP или shell.

Не входит: меню и UI 004, LLM-клиент 005, процессы и оркестрация 006,
сквозные прогоны 007, guard_apply_patch, полная проверка чтения секретов,
Fast, постоянные разрешения, корпоративные политики, другие агенты,
универсальный shell-анализатор и гарантия изоляции ОС.

## Критерии приёмки

1. Принятый контракт однозначно описан и используется зависимыми спецификациями.
2. Реализована проверка входного JSON и конфигурации; некорректные данные блокируются.
3. Правила покрывают первый набор категорий и заявленные формы; известный риск
   имеет причину. Есть тесты ложных совпадений, неопределённости и границ анализа.
4. Политики меняют ask на block; любой запрет имеет приоритет. Без совпадений —
   ask, включая ls; в Paranoid нет allow. Запрет не зависит от объяснения LLM.
5. Реализован неизменяемый снимок; повтор даёт новый actionId, исходные и вложенные
   объекты не позволяют подменить параметры. Агентские approved-поля отклоняются.
6. Тесты ядра проходят без OpenCode, сети, реального исполнения команд и UI.
   Отчёт содержит команды запуска, результаты и ограничения; Александр выполняет ревью.

## Проверка и автотесты для кода

Проверить обязательные/лишние поля, типы, null/массив, пустые строки/NUL;
корень, вложенную папку, файл вместо cwd, отсутствующий и относительный путь,
соседнюю папку с похожим префиксом, ссылки внутрь/наружу. Временные фикстуры
создавать отдельно от рабочих файлов. Проверить политики ask/block,
конфликт нескольких правил, неизвестные/составные команды и quoted-текст,
новое правило в реестре, новый UUID, неизменяемость вложенных данных.
Матрица: вход → ожидание → факт → тест. Никакие опасные команды не исполнять.

Для границ 004/005/006 достаточно контрактных фикстур; их успех не доказывает
готовность реального подтверждения или исполнения. Полный цикл проверяется
в 006/007, реальный LLM — также в 005.

## Оставшиеся технические вопросы

- Доверенный UI OpenCode/отдельный локальный интерфейс: фактическая проверка 001/004.
- Полнота покрытия конкретных форм shell: ограниченный перечень и тесты при реализации,
  расширение за пределы перечисленных категорий требует отдельного решения.
- Численные лимиты процесса/вывода и среда исполнения фиксируются до кода 006.

Эти вопросы не мешают начать независимое ядро по принятому контракту.
