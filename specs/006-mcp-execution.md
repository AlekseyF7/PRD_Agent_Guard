Цель: реализовать локальный MCP-сервер с `guard_execute_command`, связать проверку, реальное объяснение и доверенное решение пользователя, затем выполнить именно разрешённую команду с ограничением времени и вывода.

Планируемый сценарий — удаление специально созданного тестового файла. Agent Guard исполняет команду сам и возвращает результат; не предлагает агенту выполнить её другим инструментом.

Контракт принят в 003; [результаты опытов](../docs/research/pre003/README.md) есть для OpenCode v2.4.2. Доверенное подтверждение в настоящем UI ещё не проверено. Спецификации не доказывают готовность реализаций; механизм согласия не выбирать по догадке.

## Входные данные

- Вызов `guard_execute_command` по принятому в 003 контракту: команда и рабочая папка; внутренние идентификатор, снимок действия и результат проверки формирует Agent Guard.
- Ядро 003 и клиент 005 с настройками `baseURL`, `model`, источником ключа при необходимости и `timeoutMs`.
- Проверенный в 001 и принятый Алексеем канал подтверждения, реализуемый в 004. Его семантика: запрос для конкретного действия, ожидание, разрешение один раз / отказ / отсутствие ответа / ошибка.
- Согласованные ограничения времени выполнения команды и объёма сохраняемого/возвращаемого вывода. До реализации численные значения и единицы фиксирует Алексей; это технические ограничения, а не SLA заказчика.
- Зафиксированная среда запуска, согласованная демонстрационная команда и тестовая рабочая папка из 003.

## Ожидаемое поведение

### 1. Запуск и MCP-инструмент

Подготовить воспроизводимую команду запуска локального сервера. Инструмент доступен MCP-клиенту и принимает только аргументы согласованного контракта 003.

Настройки проверяются до обработки опасного действия. При ошибке запуска или конфигурации возвращается понятная причина; выполнение команды не начинается.

Передавать клиенту 005 единый набор baseURL/model/timeoutMs/authMode и источник
ключа: окружение либо адаптер системного хранилища из 004. Секрет не является
MCP-аргументом и не попадает в обычный JSON. При изменении настроек LLM отменять
ожидающие попытки, как при смене политик; новый запрос использует новые настройки.
При authMode=none не читать старый облачный ключ. Меню и подтверждение выбора
ключа при смене адреса относятся к 004, сетевой вызов и промпт — к 005.

При использовании MCP stdio не смешивать протокольный поток с логами или интерактивным вводом. Не запрашивать человеческое подтверждение через stdin MCP-процесса.

### 2. Полный цикл

1. Принять запрос, проверить его через 003 и зафиксировать параметры.
2. При некорректном запросе или запрете вернуть причину без выполнения. Несрабатывание правила обрабатывать только по принятой политике 003; не считать его доказательством безопасности.
3. Для ask получить available/unavailable через 005. При block сразу вернуть причину, без вызова LLM, подтверждения или исполнителя. Ошибка, тайм-аут и пустой ответ LLM сами не разрешают исполнение.
4. Передать в 004 то же действие, риск и состояние объяснения. При unavailable требуется отдельное allow_once_without_explanation; обычное allow_once допустимо только при available. До решения пользователя команда не запускается.
5. Принять разрешение только из доверенного канала, для ожидающего решения и тех же зафиксированных параметров.
6. При соответствующем состоянию объяснения разовом разрешении запустить именно эту команду в этой папке. Отказ, отсутствие ответа, ошибка канала подтверждения и отмена до старта завершают попытку без исполнения. Изменение настроек отменяет ожидающее решение; поздний ответ LLM или UI не меняет завершённую попытку.
7. Вернуть результат исполнения либо причину невыполнения.

Текст агента, аргумент `approved=true`, идентификатор действия и текст LLM не являются согласием. Доверенный канал не сводится к наличию идентификатора в доступном агенту запросе.

Настройки политик загружать отдельно от MCP-аргументов, валидировать через 003.
При смене настроек отменять ожидающие попытки. Перед запуском повторно
проверять канонический cwd и определимые цели на изменение относительно снимка;
при несовпадении прекращать попытку и требовать новый цикл. Проверка не является
блокировкой файловой системы и не исключает все гонки.

### 3. Однократность и неизменность

Изменение исходного объекта запроса после проверки не меняет исполняемое действие. Команда и папка, показанные пользователю, должны совпадать с фактически переданными исполнителю.

Изменение параметров требует новой проверки, объяснения и решения. Новый вызов инструмента требует нового разрешения даже при той же команде.

Повторное или запоздалое сообщение о согласии не запускает действие второй раз. Для одной попытки только один переход к выполнению; проверить также два почти одновременных сообщения о разрешении. Разрешение завершённой, отменённой или завершившейся ошибкой попытки не используется повторно.

При разрыве соединения до запуска действие не начинать; позднее согласие для прекращённой попытки не принимать. После сбоя или перезапуска не повторять команду автоматически. Если выполнение уже началось, не обещать откат или отсутствие изменений: отличать известный результат от неизвестного.

Постоянное хранилище разрешений и гарантия однократности через произвольные сбои ОС в задачу не входят.

### 4. Выполнение и ограничения ресурсов

Зафиксировать в инструкции среду и способ запуска команды по принятому формату 003. Не добавлять скрытые аргументы или другой рабочий каталог после согласия пользователя.

Ограничить время работы команды отдельно от `timeoutMs` клиента LLM и ожидания пользователя. При превышении предела прекратить выполнение в проверяемой среде и вернуть признак тайм-аута. Прекращение не означает откат уже сделанных изменений.

Ограничить объём накопленного и возвращаемого вывода; не накапливать неограниченный вывод в памяти с последующим обрезанием. При усечении явно обозначить это. Зафиксировать, как лимит применяется к stdout/stderr и в каких единицах.

Различать невозможность запуска, обычное завершение, ненулевой код выхода и тайм-аут. Ошибка процесса не должна выглядеть как успешное выполнение. Усечение вывода само по себе не доказывает ошибку команды.

### 5. Результат и ошибки

Вход действия и межкомпонентный обмен следуют 003. Итоговый MCP-результат 006 должен различать следующие состояния; точную сериализацию зафиксировать вместе с реализацией:

| Случай | Что должен различать получатель |
|---|---|
| Не выполнено | Действие не запускалось; причина: валидация, запрет, отсутствие явного согласия без объяснения при ошибке LLM, отказ, отсутствие решения, ошибка подтверждения или отмена до старта. |
| Завершено | Идентификатор действия, код выхода и ограниченные stdout/stderr; признак усечения при необходимости. |
| Ошибка исполнения | Ошибка запуска или тайм-аут; доступные сведения о процессе и ограниченный вывод. Возможные изменения не отрицаются. |
| Результат неизвестен после сбоя | Не объявлять успех, безопасную блокировку или отсутствие изменений без свидетельства; автоматического повторного запуска нет. |

Пользователь должен понимать, какой этап завершился ошибкой. Не возвращать секреты и данные авторизации в диагностике. Для демонстрации использовать только команды и вывод на тестовых данных.

### 6. Инструкция и свидетельства

Подготовить конфигурационный пример без секретов и `docs/research/mcp-execution-checks.md`: запуск сервера, зависимости, настройки, принятые лимиты, тестовые данные, сценарии и результаты.

Для 004 передать команду запуска, схему инструмента и ошибки, согласованный обмен с подтверждением. Для 007 — версию сборки, инструкции, лимиты, модель и ограничения. В 006 выполнить собственную проверку полного цикла; итоговую серию измерений 007 не дублировать.

## Ограничения

- До доверенного разрешения процесс команды не создаётся. Проверка, объяснение и ожидание не выполняют защищаемое действие.
- Ошибка LLM, отказ и отсутствие ответа не разрешают выполнение.
- Идентификатор и согласие связаны с зафиксированными параметрами; данные агента не заменяют источник доверия.
- Все изменяющие опыты — только на тестовых данных; после каждого опыта восстанавливать исходное состояние.
- Секреты не сохраняются в конфигурационных примерах, репозитории и отчётах.
- MCP-сервер защищает вызовы через собственный инструмент. Закрытие обходов OpenCode относится к 001/004, а не доказывается тестами сервера.
- Ограничение рабочей папки и времени не объявляется полноценной изоляцией средствами ОС.

## Границы задачи

Входит: локальный MCP-сервер, `guard_execute_command`, связывание 003/005/004, ожидание решения, однократное выполнение, ограничение времени/вывода, результат и инструкция.

Не входит: выбор новой архитектуры или стека, повторное исследование API OpenCode, интерфейс пользователя 004, новые правила риска 003, реализация клиента 005, итоговые метрики 007 и защита 008.

Не входят другие агенты, `guard_apply_patch`, постоянные разрешения, режим Fast с автопропуском, автоматическая установка, Docker-помощник и публикация npm.

## Критерии приёмки

Дополнение 28.11.2026 в рамках 004: доверенный UI-канал поддерживает применение
проверенных настроек к сервису, отмену pending и передачу ключа из SecretStorage
только в память. MCP-инструменты/аргументы не расширяются административными
операциями. История сессии добавляется по согласованному поручению 004.

1. Сервер запускается по инструкции; MCP-клиент обнаруживает и вызывает `guard_execute_command` с принятой схемой. Ошибочный запрос не запускает процесс.
2. В обычном полном проходе реальное объяснение LLM получено до решения пользователя. Пока решение ожидается, тестовый файл сохраняется и исполнитель не вызван.
3. Отказ, отсутствие ответа, ошибка подтверждения и отмена до старта исключают запуск. При ошибке/тайм-ауте/пустом ответе LLM запуск возможен лишь после отдельного доверенного allow_once_without_explanation; обычное allow_once отвергается. Запрет политики не вызывает LLM или UI согласия.
4. Разрешение один раз запускает именно показанную команду в показанной папке и возвращает результат. Новый вызов требует нового согласия.
5. Изменённые параметры, поддельное, повторное и запоздалое согласие не используют старое разрешение. Два сообщения о согласии не вызывают два запуска.
6. Время выполнения и вывод ограничены зафиксированными значениями. Тайм-аут, усечение, ошибка запуска и ненулевой код выхода корректно отражены в результате.
7. После разрыва до старта команда не запускается; после сбоя нет автоматического повтора. Неизвестный результат не объявляется успешным или безопасно отменённым.
8. Александр воспроизводит запуск и основные сценарии по инструкции. Сохранены результаты тестов, свидетельства реального прохода и список непроверенного.

## Проверка и автотесты для кода

Автотестами с управляемыми зависимостями проверить валидацию/запрет, ошибку и тайм-аут LLM, ожидание, отказ, отсутствие решения, ошибку подтверждения и отмену до старта. До явного согласия во всех этих случаях проверять ноль запусков исполнителя. Дополнительно проверить ровно один запуск после allow_once_without_explanation при unavailable, отказ при несовместимом типе согласия и отмену при смене настроек. При block убедиться, что не вызваны LLM и UI.

Проверить фиксацию параметров, поддельное решение, повторный вызов, повторное/позднее и два почти одновременных разрешения. Для одной разрешённой попытки ожидать ровно один вызов исполнителя с теми же параметрами.

На безопасных тестовых процессах проверить успешное завершение, ненулевой код, ошибку запуска, превышение времени и большой вывод. Подтвердить соблюдение лимитов и признаки тайм-аута/усечения. Команды, создающие дочерние процессы, если они входят в принятый демонстрационный способ запуска, проверить на прекращение; ограничения явно записать.

Отдельно выполнить полный цикл через MCP с реальной LLM и доверенным интерфейсом 004: ожидание, отказ, разрешение и повтор. Тестовая заглушка согласия не доказывает доверенность реального канала.

В `docs/research/mcp-execution-checks.md` сохранить таблицу: сценарий, вход, ожидаемый/фактический результат, число запусков, состояние файлов до/после и свидетельство. Указать среду, версию сборки, модель, лимиты и фактические команды проверок без секретов.

Александр повторяет запуск и проверяет соответствие контрактам. Найденные дефекты и непроверенные свойства передаются в 007.

## Открытые вопросы

1. Контракт принят в 003. До подключения требуются реализация ядра и проверка совместимости форматов, не новое согласование уже принятых продуктовых решений.
2. Какой способ доверенного подтверждения проверен в 001 и принят для 004/006? Нужно зафиксировать ожидание, отмену и разрыв соединения; MCP stdio и данные агента согласие не заменяют.
3. Какие пределы времени команды и объёма вывода принимает Алексей, в каких единицах и с какой областью применения к stdout/stderr? Также требуется зафиксировать среду и способ запуска принятого формата команды. Численные значения не выводятся из несуществующего SLA.

Эти решения необходимы до зависимой реализации и окончательной приёмки. До них допустим явно обозначенный минимальный серверный пример, но не заявление о готовом безопасном исполнителе.

## Уточнения команды перед реализацией 006 — 27.11.2026

Источник — обсуждение с Алексеем; это план команды, не подтверждение готовности
интеграций. Код 006 до завершения предварительного обсуждения не начинается.

### Принято

- Целевые ОС первого объёма — macOS и Windows. Проверка только на macOS не
  означает проверенную поддержку Windows; нужен отдельный реальный прогон.
- Начальный предел исполнения команды — 120000 мс. Это время после запуска
  процесса, отдельно от ожидания LLM и решения пользователя. Оно не ограничивает
  время размышления локальной модели; для LLM применяется timeoutMs клиента 005.
- Сохраняемый вывод — не более 64 KiB на stdout и отдельно 64 KiB на stderr;
  усечение обозначается явно. Начальное ожидание человеческого решения —
  120000 мс; отсутствие решения не запускает команду. Ограничения ожидания
  MCP-клиента проверяются отдельно: он может прекратить вызов раньше.
- В первом объёме одна активная попытка на экземпляр сервера: проверка,
  объяснение, ожидание или исполнение. Одновременный следующий вызов получает
  BUSY без LLM/подтверждения/исполнения. Не создаётся скрытая фоновая очередь.
  Это временное ограничение для Демо 2, не окончательное поведение продукта.
  После Демо пересмотреть очередь, несколько сессий и одновременные карточки;
  разовое согласие должно оставаться привязанным к отдельной попытке.
- Реализацию UI 004 берём на себя, не ожидаем готового интерфейса Александра.
  Функциональные границы 004 (UI) и 006 (сервер/исполнитель) сохраняются;
  выбран отдельный локальный браузерный UI, переносимый позднее в Webview VS Code через тот же контракт. Перенос требует реализации и проверки, не обещается автоматическим.
- После базового сквозного сценария приоритет интеграций — GigaCode и Codex
  в VS Code, затем их отдельные приложения. GigaCode у команды пока не установлен.
  Общая IDE не доказывает одинаковые ограничения встроенных инструментов.

### Окончательный выбор и границы первого этапа

- UI — браузерная панель, связываемая с сервером через локальный API.
  Подтверждение не является MCP-инструментом. API слушает только loopback,
  проверяет Host/Origin и отдельный случайный секрет сессии, не actionId.
  Секрет не передаётся в MCP-результат, stdout, конфигурацию проекта или процесс
  команды; ссылка панели доступна пользователю через отдельный локальный launcher.
- Это прикладное разделение каналов, не защита от произвольных программ с правами
  того же пользователя. Конфигурация агента должна ограничить обходные инструменты,
  чтение служебных файлов вне workspace и доступ агента к UI; без этой проверки
  не объявлять полный доверенный сценарий интеграции принятым.
- Минимальная панель подтверждения реализуется вместе с 006. Полное меню
  политик/LLM и OS-хранилище ключей остаются частью 004 и требуют отдельной
  реализации; не объявлять их готовыми по наличию карточки.
- macOS использует /bin/sh -c, Windows — штатный Windows PowerShell через
  powershell.exe -NoLogo -NoProfile -NonInteractive -EncodedCommand.
  Исходная команда кодируется в UTF-16LE/Base64 без подстановки другой команды;
  профиль оболочки показывается в карточке и фиксируется на попытку.
- Для Windows применяется отдельный ограниченный анализ PowerShell. Он не
  использует POSIX-экранирование путей: Remove-Item и алиасы rm/ri/del/erase/rd/rmdir
  дают риск удаления, известные литеральные цели проверяются по реальным путям.
  Git-правила переиспользуются только для разобранных аргументов. Составные,
  динамические и неизвестные формы получают partial/unknown и ask при отсутствии
  обнаруженного запрета. Это не полный анализ PowerShell.
- POSIX timeout/cancel останавливает группу процессов; Windows использует
  taskkill /T /F. Фактическую остановку дочерних процессов и кодировку вывода
  проверить отдельно на Windows. Это не OS-песочница и не поддержка демонов.
- Ключи LLM и секрет панели не наследуются окружением исполняемой команды.
  Для первого объёма используются необходимые системные переменные и PATH;
  пользовательские env для команд потребуют отдельной настройки позже.
- Перед запуском перепроверяются правила/канонические цели и отпечатки
  известных файлов (существование, inode/dev, размер, mtime). Изменение отменяет
  попытку без исполнения. Это консервативная проверка, не блокировка файловой системы.
- Смена конфигурации отменяет ожидающие попытки; новый запрос использует новый
  экземпляр ядра/LLM/исполнителя. Нет автоматического повторного запуска после сбоя.
- Windows-прогон выполняет Алексей на своём Windows 11 либо Александр на ноутбуке.
  До фактического прогона Windows остаётся непроверенной, даже если тесты построения
  аргументов и отдельного анализатора проходят на macOS.
- Самопроверка 006 включает управляемый LLM API, настоящий MCP-клиент и безопасные
  синтетические процессы. Реальный OpenCode/Codex/GigaCode, облачная LLM в полном
  цикле и ручной браузерный UI отмечаются отдельными проверками.


### Уточнение ручного проверочного клиента и обратной связи

В первом ручном прогоне guard:check клиент закрывал соединение сразу после
единственного ответа, что не позволяло панели надёжно показать результат
быстрой команды. Диагностический клиент по умолчанию теперь сохраняет сессию
и предлагает Enter для новой безопасной команды либо q для завершения. Для
автоматизации оставляется --once. Согласие по-прежнему выдаётся только через UI.
SIGINT/закрытие клиента завершает сервер и отменяет активную попытку.
Реальный агент определяет срок жизни своего MCP-процесса отдельно.
Обновление UI не должно скрывать результат при потере связи или оставлять
доступными устаревшие кнопки согласия. Последний известный результат и
потеря соединения показываются как разные состояния.
