## Источник и цель

Источники: [спринт](../SPRINT.md), [бэклог](../BACKLOG.md),
[правила](../AGENTS.md), [README](../README.md),
[архитектура](../docs/architecture.md), [требования](../docs/requirements.md),

Последнее уточняет устаревшие ограничения исходного плана; это не отчёт о реализации.

Цель: подключить локальный MCP-сервер Agent Guard к исследованной версии OpenCode, применить проверенные ограничения обхода, реализовать интерфейс доверенного подтверждения и подготовить воспроизводимую инструкцию запуска.

Контракт 003 принят 27.11.2026. Есть [результаты опытов OpenCode v2.4.2](../docs/research/pre003/README.md), но доверенный UI ещё не подтверждён. Подключение MCP и протокольные тесты не доказывают готовность полного сценария.

Архитектура сохраняется: Agent Guard сам выполняет разрешённую команду через `guard_execute_command`; OpenCode не получает рекомендацию выполнить её встроенным терминалом.

## Входные данные

- Отчёт, минимальный MCP-пример и проверенная конфигурация из 001: точная версия OpenCode, среда, запреты, способы обхода и кандидат доверенного подтверждения.
- Принятый контракт 003: действие, зафиксированные параметры, результат правил, объяснение, решение и ошибки. Имена полей не выбирать независимо в 004.
- Команда запуска и конфигурация сервера из 006; настройки LLM из 005: `baseURL`, `model`, отдельный источник ключа при необходимости, `timeoutMs`.
- Отдельный тестовый проект с файлом для удаления и файлом для чтения; согласованная демонстрационная команда и допустимая рабочая папка.
- Безопасный пример конфигурации без ключей и персональных путей.

## Ожидаемое поведение

### 1. Подключение и ограничения OpenCode

На версии из 001 подготовить конфигурацию запуска Agent Guard и подключения его MCP-инструмента. Зафиксировать, какие настройки применяются, где размещаются и как проверить, что активна именно эта конфигурация.

Применить проверенные в 001 ограничения:

- запрет встроенного терминала и других доступных способов исполнения команд;
- запрет встроенных записи, редактирования и применения изменений;
- запрет обхода через делегирование;
- отключение или ограничение других MCP-серверов и расширений, способных выполнить защищаемую операцию.

Сохранить разрешённое чтение и вызов `guard_execute_command`. Не заменять запреты текстовым обещанием агента соблюдать правила.

Перечень ограничений относится к конкретной конфигурации. Отсутствующий инструмент отмечать как отсутствующий, а непроверенный путь — как непроверенный. Если выводы 001 не воспроизводятся, вернуть блокер Алексею и не объявлять обязательность проверки обеспеченной.

### 2. Интерфейс подтверждения

Реализовать выбранный по результатам 001 и согласованный Алексеем способ подтверждения: встроенный механизм OpenCode либо минимальный отдельный локальный интерфейс. Новый способ без проверки не выбирать.

Перед решением пользователь видит:

- точную зафиксированную команду и рабочую папку;
- объяснение реальной LLM для этого действия либо явное предупреждение о его недоступности;
- найденный правилом риск;
- действия «разрешить один раз» и «отказать».

Интерфейс передаёт решение для того же действия по контракту 003. Он не изменяет параметры и не исполняет команду самостоятельно. Исполнение и контроль однократного разрешения принадлежат 006.

Пока решения нет, интерфейс показывает ожидание; действие не выполняется. Отказ, закрытие интерфейса, отсутствие ответа и ошибка канала не превращаются в разрешение. Если требуется срок ожидания, его поведение согласуется с 006; произвольный тайм-аут в 004 не вводится.

Новый вызов требует нового решения. При изменении команды или папки старое подтверждение не переносится. Текст агента и поле `approved=true` не считаются согласием. Агент не должен иметь доступного в этой конфигурации способа самостоятельно выдать решение через выбранный канал.

MCP stdio не использовать как интерактивный терминал подтверждения.

### 3. Результаты и ошибки

После обработки пользователь может отличить выполнение, отказ и ошибку. Результат команды и причину невыполнения получать от 006; не подменять ошибку сообщением об успехе.

Проверить и описать поведение при недоступном сервере, ошибке подключения, ошибке/тайм-ауте LLM, недоступном интерфейсе подтверждения и потере соединения во время ожидания. Автоматическое повторение опасной команды при восстановлении соединения не вводить.

При unavailable показывать предупреждение и «Разрешить один раз без объяснения»/«Отказать»; при available — «Разрешить один раз»/«Отказать». Во время запроса LLM показывать ожидание. Решение передавать по контракту 003; ошибка LLM сама не разрешает исполнение. При block показывать причину без кнопки разрешения и без запроса LLM. Успешная проверка с реальной моделью остаётся обязательной отдельно от деградированного сценария.

### 4. Меню политик — цель к Демо 2

При первом подключении и повторном открытии настроек дать выбор block/ask
для реализованных категорий 003: file_delete, git_destructive, git_force_push,
outside_workspace. Начальные значения — из 003, режим Paranoid. Выбор сохранять
в JSON и загружать после перезапуска; место хранения указать по реализации,
не принимать настройки из MCP-аргументов действия. Не показывать работающими
неподдержанные категории (например, полную защиту чтения секретов).

Проверять настройки по схеме 003, ошибку сохраняемого значения показывать
без изменения действующей политики. Изменение отменяет pending-решения
и требует новой проверки по 006. Отключение блока означает ask.
Fast, постоянные разрешения, корпоративная защита и тест знаний не входят.
Если меню не успели — явно зафиксировать перенос; ручной JSON не считать меню.

### 5. Настройки LLM — цель к Демо 2

В том же меню дать настройку baseURL, model, timeoutMs и authMode (apiKey/none),
поле ввода/замены ключа, удаление сохранённого ключа и кнопку «Проверить подключение».
Проверка использует клиент 005 и синтетическое действие; она не запускает команду
и не выдаёт разрешение для ожидающего действия. Показать успех либо безопасную
причину ошибки. Это дополнение команды от 27.11.2026; возможность UI ещё нужно реализовать.

Несекретные значения сохранять в локальном JSON вне файлов репозитория; секрет —
в системном хранилище учётных данных, с credentialRef в настройках. Пользователь
вводит ключ один раз и может заменить/удалить его позже. В UI показывать только
статус наличия ключа, не возвращать сохранённый секрет в форму/диагностику.
Нельзя включать секрет в JSON, MCP-аргументы или текст объяснения. Маска поля
не является способом хранения. Источник окружения из 005 остаётся доступен
для разработки, без копирования его значения в обычный файл настроек.

Адаптер системного хранилища реализуется в 004 и передаётся через интерфейс
источника ключа 005. Поддерживаемые ОС и условия доступа фиксируются по проверке.
Если хранилище недоступно — показать ошибку, не сохранять ключ открытым текстом.
Не обещать корпоративную неизменяемость или защиту от всех программ того же пользователя.

При смене baseURL старый ключ не передавать новому адресу автоматически:
пользователь заново выбирает/подтверждает источник ключа либо none. При сохранении
новых настроек ожидающие попытки отменяются через 006; следующий запрос использует
новый согласованный набор адреса, модели и источника. Облачное и локальное
подключение используют один клиент и промпт 005. Установка локальной модели
через меню и управление Ollama не входят.

Меню политик и LLM проверять отдельно. Отсутствие меню явно записать как
невыполненную часть 004; ручной конфиг не объявлять полноценным интерфейсом.

### 6. Инструкция и передача результатов

Результаты:

- проверенная конфигурация OpenCode и необходимые файлы интеграции/интерфейса; фактические пути перечислить в отчёте;
- `docs/research/opencode-integration.md` — инструкция и свидетельства проверки.

Инструкция содержит версию и среду, зависимости, безопасные настройки, способ ввода ключа в меню/хранилище и альтернативу через окружение, запуск сервера и интерфейса, подключение OpenCode, применение запретов и проверку активной конфигурации. Точные команды брать из работающей сборки.

Описать создание тестовых файлов, разрешение и отказ, проверку чтения, восстановление исходного состояния и завершение работы. Другой участник должен воспроизвести запуск без устных дополнений.

Для 007 передать версию сборки, конфигурацию, команды запуска, сценарии, ожидаемые результаты, свидетельства и оставшиеся ограничения. Финальный набор прогонов и измерение задержек остаются в 007.

## Ограничения

- Все изменяющие проверки выполняются только на специально созданных тестовых данных.
- Секреты не сохраняются в репозитории, инструкции, логах и записи экрана.
- Решение пользователя относится только к показанным параметрам; данные агента не являются доверенным подтверждением.
- Проверенная конфигурация OpenCode не объявляется изоляцией средствами ОС или защитой от ручных действий пользователя.
- При найденном обходе или непроверенном источнике согласия полный защищённый сценарий не считается принятым. Решение о сокращённом показе принимает Алексей по SPRINT.md.

## Границы задачи

Входит: конфигурация подключения и ограничений, меню политик и LLM, адаптер системного хранилища ключей, интерфейс подтверждения, необходимая интеграционная обвязка, инструкция и проверка её воспроизводимости.

Не входит: повторное самостоятельное исследование другой версии OpenCode, изменение архитектуры, ядро и правила 003, LLM-клиент 005, сервер и исполнитель 006, итоговые прогоны и метрики 007, материалы защиты 008.

Не входят постоянные разрешения, режим Fast с автопропуском, другие агенты, изменение файлов через `guard_apply_patch`, Docker-помощник и публикация npm. До Демо достаточно ручной воспроизводимой установки.

## Критерии приёмки

1. На версии из 001 OpenCode подключается к готовому серверу и вызывает `guard_execute_command`; конфигурация и фактические команды запуска сохранены.
2. Попытки прямого выполнения, встроенного редактирования и доступных способов делегирования заблокированы. Другие пути учтены по 001; разрешённое чтение и вызов Guard работают.
3. До решения видны точная команда, папка и известный риск; в обычном сценарии — реальное объяснение LLM, в деградированном — предупреждение и явное разрешение без объяснения. До решения файл остаётся на месте.
4. Отказ сохраняет файл. Разрешение один раз выполняет именно показанное действие через 006. Повторный вызов запрашивает новое решение; изменённые параметры не используют старое согласие.
5. Поддельное согласие от агента не разрешает действие. Закрытие интерфейса, отсутствие ответа и ошибки подключения/подтверждения не запускают команду; ошибка LLM требует отдельного явного согласия без объяснения и не показываются как успех.
6. Алексей воспроизводит запуск и основные сценарии по инструкции в чистом тестовом проекте. Версия и среда повторного запуска записаны.
7. Меню открывается при подключении и повторно, выбор сохраняется и применяется после перезапуска; неверные настройки не применяются, ожидающее решение при смене политики отменяется. При block нет кнопки разрешения.
8. Настройки LLM сохраняются между запусками: несекретный JSON и ключ отдельно
   в системном хранилище. Проверены ввод/замена/удаление ключа, ошибка хранилища,
   проверка подключения без исполнения, none без Authorization, смена адреса
   без автоматической передачи старого ключа; ключа нет в JSON/логах/результатах.
9. Результаты переданы для 007. Непроверенное и найденные обходы перечислены; они не скрыты формулировкой «интеграция работает».

## Проверка и автотесты для кода

В `docs/research/opencode-integration.md` сохранить таблицу: сценарий, версия/конфигурация, шаги, ожидаемый и фактический результат, состояние файлов до/после, ссылка на лог или запись без секретов.

Проверить подключение, разрешённое чтение, попытки обхода, ожидание, отказ, разрешение один раз, повтор, изменение параметров и попытку подделки согласия. Отдельно проверить недоступность сервера, ошибку LLM и закрытие/ошибку интерфейса. Для ожидания сначала зафиксировать сохранность файла, затем завершить опыт отказом или закрытием интерфейса.

Дополнительно проверить сохранение/замену/удаление секрета, недоступное хранилище,
перезапуск, смену облачного адреса на локальный и отмену ожидающего действия.
Для адаптера хранилища нужны тесты с управляемой подстановкой плюс реальная
проверка на поддерживаемой ОС без публикации ключей.

Если 004 добавляет программную обвязку, нужны уместные автотесты связи решения с действием, отказа и ошибок канала, отсутствия доверия к данным агента. Механизм запретов OpenCode и полный цикл дополнительно проверяются вручную на реальной конфигурации. Для одних конфигурационных файлов не создавать бессмысленные автотесты.

Алексей повторяет запуск по инструкции и проверяет результат. Точные команды проверок, результаты, дефекты и непроверенные случаи сохраняются в отчёте. Тест с заглушкой не заменяет итоговый проход с реальной LLM.

## Открытые вопросы

- На OpenCode v2.4.2 есть результаты ограниченных опытов; настоящий доверенный UI ещё нужно подтвердить. Не реализовывать его по предположению об API.
- Поля действия, политик и обмена приняты в 003; не создавать независимые несовместимые схемы.
- Фактическая команда запуска сервера и ограничения ожидания/возврата определяются в 006. До их появления можно готовить интеграцию с явно обозначенным минимальным примером, но нельзя объявлять сквозную приёмку завершённой.


## Выбор UI команды для первого этапа 006

27.11.2026 Алексей выбрал общую локальную браузерную панель. Минимальная
карточка подтверждения разрабатывается нами в связке с 006; работа Александра
по ревью/локальной модели не блокирует её реализацию. Впоследствии возможен
собственный Webview Agent Guard в VS Code с тем же контрактом обмена.
Это не встраивание карточки в чужой чат и не готовая интеграция агентов.
Полное меню политик/LLM и системное хранилище ключей остаются критериями 004;
минимальная карточка их не заменяет. Доверенность канала и запреты обходов
проверяются на каждом клиенте отдельно.
