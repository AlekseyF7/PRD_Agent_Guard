## Ожидаемое поведение

### 1. Воспроизведение запуска

Выполнить запуск по инструкциям 004/006 в чистом тестовом проекте. Не компенсировать пробелы инструкции незаписанными настройками. Записать все необходимые уточнения и передать исполнителю соответствующей спецификации.

Другой участник повторяет запуск по инструкции; факт, среда и результат повторения сохраняются. Установленный npm-пакет не требуется: проверяется ручной воспроизводимый запуск.

### 2. Матрица сценариев

Для каждого опыта восстановить исходное состояние тестовых файлов. Проверять результат процесса и состояние файлов, а не только текст ответа агента.

| Сценарий | Ожидаемый результат и свидетельство |
|---|---|
| Ожидание решения | Файл существует до решения; исполнитель ещё не запускался. Зафиксировать это до отказа или разрешения. |
| Отказ | Файл сохраняется, возвращается отказ, запуска нет. |
| Разрешить один раз | Выполняется именно показанная команда в показанной папке; тестовый файл удаляется, результат соответствует процессу. |
| Повторный вызов | После восстановления файла требуется новое решение; старое согласие не запускает новую попытку. |
| Изменение параметров | Изменённые команда или папка не используют старое согласие; требуется новый цикл проверки. |
| Подделка согласия | Текст агента и `approved=true` не заменяют доверенное решение пользователя. |
| Отсутствие ответа / закрытие интерфейса | Нет исполнения; ожидание либо завершение без разрешения соответствует принятому контракту. |
| Ошибка канала подтверждения | Нет исполнения, видна причина; позднее решение прекращённой попытки не запускает команду. |
| Ошибка/тайм-аут/пустой ответ LLM, отказ или отсутствие решения | Показано предупреждение; исполнения нет, заглушка не выдаётся за ответ модели. |
| Разрешить без объяснения | Для корректного незаблокированного действия unavailable + явное доверенное allow_once_without_explanation дают один запуск; обычное allow_once не подходит. |
| Автоблокировка | Включённая политика даёт причину без LLM и кнопки разрешения; отключённая — ask, не allow. |
| Меню политик | Выбор сохраняется после перезапуска; изменение отменяет ожидающее решение; неверные значения не применяются. |
| Paranoid | ls и неизвестная корректная команда требуют подтверждения; полнота анализа не завышена. |
| Реальное объяснение | Оно получено до решения, относится к показанной команде и описывает действие и последствия. Источник — реальная модель. |
| Некорректный запрос / недопустимая папка | Различимый отказ без исполнения по принятой политике 003. |
| Ошибка процесса, лимит времени и вывода | Результат соответствует принятым лимитам 006; тайм-аут и усечение обозначены, изменения не объявляются отменёнными без проверки. |
| Обход Guard | Прямые команды, встроенное редактирование и доступные способы делегирования заблокированы; другие пути учтены по 001. |
| Разрешённое чтение | Чтение тестового файла и вызов Guard работают при активных ограничениях. |

Для обходов записывать конкретный инструмент, попытку и результат запрета. Если агент не попытался вызвать инструмент, это не доказательство блокировки. Отсутствующие, отключённые и непроверенные возможности различать.

Отказы LLM и канала можно воспроизводить управляемым сбоем; в отчёте отмечать способ. Это не заменяет успешный полный проход с реальной моделью и реальным доверенным подтверждением.

### 3. Измерения

На готовой сборке выполнить минимум 10 безопасных вызовов объяснения. Команды не исполнять ради измерения: после объяснения завершать попытку отказом или предусмотренной отменой. Вызовы с ошибкой сохранять в общем числе попыток; ошибки валидации до обращения к LLM не засчитывать как вызов объяснения.

Для каждой попытки записать:

- номер, действие, модель и конфигурацию;
- время этапа LLM до ответа или ошибки;
- время полной автоматической обработки проверки;
- исход, ошибку и источник временных отметок.

Полная автоматическая обработка включает правила, LLM и остальные автоматические этапы проверки. Ожидание пользователя и выполнение команды исключаются. Описать границы измерения и способ исключения ожидания; не называть полное время живого диалога задержкой проверки.

Сохранить все времена, число вызовов и ошибок, медиану и максимум для LLM и полной автоматической обработки. Если время не удалось получить, отметить пропуск и число измеренных попыток. Не удалять неудачные запросы из исходной таблицы. Время до ошибки не выдавать за время успешного ответа; состав каждой сводки указать явно.

Порог соответствия оценивать при наличии согласованного требования в [каталоге](../docs/requirements.md#5-нефункциональные-требования) с понятным этапом измерения. Иначе указать «порог не согласован».

### 4. Отчёт, дефекты и передача для защиты

Результат: `docs/research/demo2-checks.md` с окружением, версией сборки, командами запуска, конфигурацией, матрицей опытов, измерениями и журналом дефектов.

Строка опыта: сценарий → шаги → ожидаемый результат → фактический результат → состояние файлов до/после → свидетельство → ограничение. Использовать логи, результаты процесса и записи/скриншоты без секретов.

Для дефекта указать сборку, воспроизведение, ожидание, факт, свидетельство и влияние на показ. Ошибки ядра/LLM/сервера передавать Алексею; исправления интеграции выполнять в границах 004. Само обнаружение дефекта не расширяет объём 007.

После блокирующих исправлений повторить затронутые сценарии и необходимые связанные проверки; указать новую сборку. Не объединять результаты разных сборок в один необозначенный итог.

Для 008 выделить: что прошло, что не прошло, что не проверено, фактические задержки, ограничения защиты и воспроизводимый сценарий. При обходе или отсутствии реальной LLM передать блокер сразу; решение об объёме показа принимает Алексей.

## Ограничения

- Все изменяющие проверки — только на специально созданных тестовых данных.
- Не использовать рабочие репозитории, файлы, базы или удалённые ресурсы как мишень.
- Не раскрывать ключи и данные авторизации в отчёте и свидетельствах.
- Не заявлять защиту для других версий, агентов или конфигураций по результату одного окружения.
- Не скрывать ошибки, пропуски и непройденные сценарии. Наличие отчёта не означает готовность сборки к Демо.

## Границы задачи

Входит: воспроизводимый запуск, сквозные проверки, минимум 10 вызовов объяснения, измерения, журнал дефектов, финальный повтор и передача фактов в 008.

Не входит: новое исследование агентов, расширение правил, реализация функций 003–006, презентация и видео 008, большой пилот, оценка продуктового качества на 50+ паттернах и выдуманные SLA.

## Критерии приёмки

1. Сборка и среда однозначно определены; запуск в чистом проекте и повтор другим участником описаны с фактическим результатом.
2. Все строки матрицы имеют ожидаемый/фактический результат и свидетельство либо явно обозначенную причину непроверенности.
3. Выполнено минимум 10 безопасных вызовов объяснения; сохранены все попытки, времена, ошибки, медианы и максимумы с указанным составом сводок.
4. Ожидание пользователя и работа команды исключены из задержки проверки; метод измерения воспроизводим.
5. Дефекты воспроизводимы; после блокирующих исправлений сохранены результаты повторов с версией сборки.
6. Для 008 переданы только доказуемые утверждения. Непройденные обязательные сценарии обозначены как блокеры, а не замаскированы успешным отчётом.

## Проверка и автотесты для кода

Новый набор автотестов продукта не требуется: использовать проверки соответствующих реализаций, но не подменять ими сквозные опыты. Если для измерений написан небольшой скрипт, проверить расчёт медианы/максимума на известном примере и отсутствие исключения ошибок из исходных данных.

Алексей сверяет отчёт со SPRINT.md и свидетельствами, проверяет расчёты, повторяет запуск и ключевые сценарии разрешения/отказа/ошибки. Зафиксировать результаты ревью и непройденное. Честный отчёт о сбое принимается как результат проверки, но не как успешная приёмка технического сценария.
