## Результат к пятнице

Один воспроизводимый сценарий на конкретной версии OpenCode:

**Вызов MCP → проверка команды → реальное объяснение LLM → разрешить один раз / отказать → выполнение / блокировка.**

Проверяем команду удаления специально созданного тестового файла. Отдельно проверяем запрет встроенных обходных инструментов. Реальный вызов LLM обязателен для заявления о выполнении требования объяснения; шаблон или заглушка не заменяют его.

## Как работаем параллельно

- Во вторник за первые 30–45 минут Алексей и Александр фиксируют поля действия, ответа LLM и интерфейс подтверждения: запрос, ожидание, разрешение/отказ/ошибка. Исследование идёт параллельно созданию сервера.
- Алексей владеет кодом ядра, LLM-клиента и MCP-исполнителя. Александр — конфигурацией OpenCode, интерфейсом подтверждения, интеграционными примерами и прогонами. Общие файлы меняем по договорённости.
- Александр начинает подключение с минимального примера; не ждёт готового ядра. Заглушки допустимы при разработке, но обозначаются и заменяются в итоговом показе.
- В конце каждого дня — 15 минут: показать работающий результат, назвать блокер и согласовать следующий шаг. Блокеры сообщаем сразу.
- Каждый день после ревью объединяем совместимые изменения в dev. Commit, push и merge выполняют участники по принятому процессу, не автоматически агентом.

## Что Кирилл спрашивает у студентов

Короткие интервью с **3–5 студентами**, которые пользуются или пробовали coding-агентов. Это целевой размер небольшой проверки, не достигнутая метрика и не репрезентативное исследование.

- Был ли реальный случай нежелательного изменения/удаления? Как сейчас проверяют действия агента?
- Показать один пример команды с обычным подтверждением и с понятным объяснением: что человек понял в каждом случае? Помогло ли объяснение принять решение?
- Какие сведения в объяснении нужны, что лишнее? Сколько готовы ждать?
- Когда выбрали бы «разрешить один раз», а когда постоянное разрешение для файла? Понимают ли риск постоянного разрешения и как ожидают его отменять?
- Какие операции хотят подтверждать всегда, а какие предупреждения раздражают?

Результат: `docs/research/demo2-user-feedback.md` — фактическое число участников, обезличенные ответы, способ подбора, полезные функции, сомнения и ограничения. Порядок двух примеров по возможности менять. Не выдавать намерение пользоваться за доказанный спрос; не записывать придуманные ответы при отсутствии участников.

## Приёмка технической части

Александр записывает результаты в `docs/research/demo2-checks.md`: версия OpenCode, среда, модель, команда запуска, сценарий, ожидаемый/фактический результат и свидетельство. Это целевые пути создаваемых материалов.

| Проверка | Ожидаемый результат |
|---|---|
| Ожидание решения | Тестовый файл остаётся на месте до разрешения |
| Отказ | Файл не удаляется; возвращается отказ |
| Разрешить один раз | Выполняется именно показанная команда с зафиксированными параметрами |
| Повторный вызов | Запрашивается новое решение |
| Изменённые параметры | Старое разрешение не подходит к новому действию |
| Ошибка/тайм-аут LLM | Действие не выполняется; видна ошибка |
| Объяснение | Поступает от реальной модели до решения пользователя; описывает действие и последствия |
| Обход | Прямые команды, встроенные изменения и проверенные способы делегирования заблокированы; разрешённое чтение работает |
| Повторная установка | Другой участник воспроизводит запуск по инструкции |

На готовой сборке провести минимум **10 безопасных вызовов объяснения**: записать все времена, медиану, максимум, число ошибок; не исключать неудачные запросы из отчёта. Отдельно измерить время LLM и полную автоматическую обработку. Время размышления пользователя и выполнения команды не включать в задержку проверки. Соответствие порогу оценивать только после уточнения требования.

Все действия выполняются на специально созданных тестовых данных. Согласие должно поступать от пользователя: текст агента или поле `approved=true` не заменяют его. MCP stdio не используем как интерактивный терминал подтверждения.

## Контрольные точки и сокращение объёма

- **Вторник, конец дня:** зафиксированы способ подтверждения, версия и результаты запретов. Если решение не найдено — Алексей и Александр разбирают блокер вместе, не исследуют его всю неделю без ограничения.
- **Среда, конец дня:** цель — рабочие объяснение, отказ и разрешение. Если встроенное подтверждение недоступно, допустим минимальный отдельный локальный интерфейс, доступный пользователю и не выдающий агенту полномочия согласия. Это решение требует проверки до исполнения команд.
- **Четверг, конец дня:** рабочая сборка и отчёт. При непреодолимом обходе демонстрируем только подтверждённый объём защиты и прямо называем ограничение; Кирилл согласует отклонение с заказчиком. При отсутствии реальной LLM не объявляем требование выполненным.
- **Пятница:** после финального прогона функциональность не расширяем. При сбое живого показа используем запись реальной сборки, явно называя её записью; соответствие формату Демо заранее уточняет Кирилл.

После Демо переносим: другие агенты, полный редактор файлов, постоянные разрешения и режимы строгости, калибровку, автоматическую установку, Docker-помощник, публикацию npm, широкий набор паттернов и большой пилот. До Демо обязательна ручная воспроизводимая установка. Настройки локального API сохраняем; отдельный прогон Ollama — при наличии времени, иначе отмечаем непроверенным. Перенос обязательных для заказчика функций требует явного согласования.
