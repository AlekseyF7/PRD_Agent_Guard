# Функциональные требования Agent Guard

**Версия:** 1

## 1. Назначение продукта

Agent Guard — инструмент безопасности и осознанного контроля кодинговых ИИ-агентов. Система проверяет потенциально опасные действия до их выполнения, объясняет пользователю возможные последствия и позволяет принять решение о выполнении действия.

Целевая аудитория — студенты, начинающие разработчики и другие пользователи кодинговых агентов, которым сложно самостоятельно оценивать риски технических действий. Для опытных пользователей продукт должен обеспечивать дополнительный контроль без избыточных уведомлений.

Основная задача — сохранить преимущества автоматизации, снизив риск нежелательных изменений в проекте и окружении пользователя.

## 2. Функциональные требования

Приоритеты:
- **P0** — первая рабочая версия, текущий минимальный сценарий Демо 2.
- **P1** — развитие до полноценного MVP после Демо 2
- **P2** — дальнейшее развитие; новые продуктовые гипотезы требуют проверки.

| ID | Функция | Ожидаемое поведение системы | Приоритет |
| --- | --- | --- | --- |
| FR-01 | Подключение к ИИ-агенту | Пользователь может подключить Agent Guard к OpenCode и запустить работу в поддерживаемой конфигурации. | P0 |
| FR-02 | Проверка действий до выполнения | Система принимает поддерживаемые команды агента на проверку до их выполнения. В поддерживаемой конфигурации защищаемые операции не должны выполняться в обход проверки. | P0 |
| FR-03 | Оценка риска | Система определяет, допустимо ли действие, требует ли оно подтверждения или должно быть запрещено | P0 |
| FR-04 | Объяснение действия | Система с помощью LLM объясняет понятным языком, что агент собирается сделать и к каким последствиям это может привести. Объяснение показывается до принятия решения. | P0 |
| FR-05 | Подтверждение действия | Пользователь видит конкретную команду, рабочую папку, объяснение и известные риски. Он может разрешить действие один раз или отказаться. До получения необходимого подтверждения действие не выполняется. | P0 |
| FR-06 | Выполнение или блокировка | Система выполняет именно разрешённое действие и возвращает результат агенту. При отказе или запрете действие не выполняется. Изменение параметров требует новой проверки; повторный вызов не использует прежнее разовое разрешение. | P0 |
| FR-07 | Безопасная обработка ошибок | При ошибке проверки, отсутствии необходимого подтверждения, ошибке или тайм-ауте LLM действие в первой версии не выполняется. Пользователь или агент получает понятную причину отказа. | P0 |
| FR-08 | Настройка объясняющей модели | Пользователь может настроить подключение к поддерживаемой LLM. Предусматривается выбор облачной или локальной модели через совместимый API; для Демо 2 обязательна реальная LLM | P0 / P1 |
| FR-09 | Расширенная проверка действий | Система распознаёт дополнительные категории рисков: удаление и изменение файлов, опасные операции Git, действия вне рабочей директории и другие согласованные сценарии. SQL-операции рассматриваются отдельно с учётом реализуемости. | P1 |
| FR-10 | Пропуск безопасных действий | Система не требует дополнительного подтверждения для действий, которые действующая политика однозначно разрешает. Неопределённый риск не считается безопасным по умолчанию. | P1 |
| FR-11 | Оценка последствий | Система по возможности показывает затрагиваемые файлы и ресурсы, масштаб изменений и возможность восстановления. Если последствия нельзя надёжно определить, сообщает об этом явно. | P1 |
| FR-12 | Расширенное объяснение | Пользователь может запросить более подробное объяснение незнакомой команды, её назначения, рисков и последствий, не разрешая действие автоматически. | P1 |
| FR-13 | Настройка подробности объяснений | Пользователь может выбрать краткие или более подробные объяснения в зависимости от своих знаний и предпочтений. Настройка не отключает обязательные ограничения безопасности. | P1 |
| FR-14 | Журнал действий | Пользователь может посмотреть историю проверенных действий, выявленные риски, принятые решения и доступные результаты выполнения. | P1 |
| FR-15 | Установка и настройка | Пользователь может подключить продукт по воспроизводимой инструкции и проверить готовность к работе. Для полноценного MVP предусматривается распространяемый установочный пакет. | P0 / P1 |
| FR-16 | Постоянные разрешения | Пользователь может сохранять разрешения для строго ограниченной области действий, если это допускает политика безопасности, просматривать и отзывать их. Критические запреты не отменяются сохранённым разрешением. | P2 |
| FR-17 | Режимы строгости | Пользователь может регулировать частоту подтверждений некритичных действий. Обязательные запреты и подтверждения критических действий сохраняются независимо от режима. | P2 |
| FR-18 | Обсуждение действия | Пользователь может задавать уточняющие вопросы о конкретном ожидающем подтверждения действии в отдельном диалоге. Исходное действие остаётся на паузе, основная сессия агента не должна изменяться из-за такого обсуждения. | P2 |
| FR-19 | Калибровка знаний | Система может определить рекомендуемую подробность объяснений с помощью короткого теста или других согласованных способов. Пользователь может изменить рекомендацию вручную. | P2 |
| FR-20 | Поддержка других агентов | Пользователь может подключать Agent Guard к другим кодинговым агентам после проверки совместимости и невозможности обнаруженных обходов. Приоритеты интеграций определяются отдельно. | P2 |

## 3. Основной пользовательский сценарий

1. Пользователь подключает Agent Guard и работает с ИИ-агентом.
2. Агент инициирует поддерживаемое действие, которое поступает на проверку до выполнения.
3. Agent Guard оценивает риск и определяет допустимость действия.
4. Если требуется подтверждение, система формирует объяснение через LLM, показывает действие и возможные последствия.
5. Пользователь разрешает действие один раз или отказывает.
6. Система выполняет разрешённое действие либо блокирует его и возвращает результат агенту.

В развитом MVP действия, однозначно разрешённые политикой, не требуют дополнительного подтверждения; запрещённые действия блокируются независимо от ответа LLM. В первой версии при ошибке объяснения действие не выполняется.

## 4. Общие требования и ограничения

- Объяснение должно быть понятно пользователю без глубоких знаний командной строки и не скрывать существенные риски.
- LLM не должна самостоятельно выдавать разрешение на действие или отменять запрет правил. Подтверждение поступает непосредственно от пользователя через доверенный интерфейс.
- Система не должна создавать избыточных предупреждений или задержек. Конкретные численные пороги согласуются отдельно и проверяются на работающей сборке.
- Секреты и ключи не публикуются; во внешнюю модель передаётся только необходимый разрешённый контекст.
- Защита распространяется на поддерживаемые операции и проверенные конфигурации агента. Если альтернативный путь выполнения не заблокирован, это ограничение фиксируется явно; полная защита не заявляется.
