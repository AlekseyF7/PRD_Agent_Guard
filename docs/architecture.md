# Архитектура Agent Guard

## Назначение

Agent Guard — локальный MCP-сервер для проверки опасных действий
coding-агентов перед выполнением.

Принятое решение:
[ADR-001](decisions/001-mcp-and-llm-provider.md) и
[ADR-002: контракт и пользовательские политики](decisions/002-core-contract-and-user-policies.md).
Точные поля и границы правил — в [003](../specs/003-contract-and-core.md).

Первую интеграцию реализуем и проверяем на OpenCode.

## Компоненты

| Компонент | Ответственность |
|---|---|
| MCP-слой | Принимает вызовы инструментов от агента, возвращает результаты |
| Ядро 003 | Валидирует действие и настройки, применяет правила/политики, фиксирует снимок |
| Оркестрация 006 | Связывает ядро, LLM, доверенное подтверждение и исполнитель |
| Настройки 004 | Меню политик и сохранение выбора; схема принадлежит 003 |
| Правила | Определяют риск, запреты и необходимость подтверждения |
| LLM-клиент | Получает объяснение действия через настроенный API |
| Подтверждение | Показывает действие и объяснение, получает решение пользователя |
| Исполнитель | Выполняет разрешённую команду или изменение файла |

Компоненты входят в одну локальную программу.
Отдельный сетевой микросервис для ядра не требуется.

LLM работает отдельно: в облаке либо локально у пользователя.

## MCP-инструменты

Планируем два основных вида операций:

- guard_execute_command — выполнение команды в указанной рабочей папке;
- guard_apply_patch — применение явно заданных изменений файлов.

Точные схемы аргументов фиксируются в спецификациях до реализации.

Инструмент не должен просто рекомендовать агенту выполнить действие
другим способом: разрешённое действие выполняет сам Agent Guard.

## Общее описание действия

Внутри программы действие представляется независимо от агента:

- идентификатор;
- тип операции;
- рабочая папка;
- команда либо изменения файлов;
- затрагиваемые пути, если их удалось определить;
- результат проверки правил.

Для команд нельзя считать список затрагиваемых файлов полным:
произвольная команда может иметь динамические последствия.

## Обработка действия

1. MCP-слой принимает запрос.
2. Ядро проверяет формат запроса и допустимость рабочей папки.
3. Фиксирует параметры действия.
4. Правила определяют запрет и необходимость подтверждения.
5. В режиме Paranoid незапрещённое действие получает ask; LLM формирует объяснение
   либо возвращает явную недоступность. При block сразу возвращаем причину,
   не вызываем LLM и не предлагаем разрешение.
6. Если требуется подтверждение, пользователь видит точное действие,
   рабочую папку, объяснение и найденные риски.
7. Исполнитель выполняет разрешённое действие.
8. MCP-слой возвращает результат либо причину отказа.

Ответ LLM не отменяет запрет правил.

Объяснение относится к зафиксированному действию.
Изменение команды или параметров требует новой проверки.

## Подтверждение

Первый обязательный сценарий — разрешить один раз или отказать.
При отсутствии объяснения подпись разрешения явно указывает это.
Для заблокированного политикой действия разрешение не предлагается.
Меню пользовательских политик при подключении и повторном открытии настроек
пытаемся реализовать к Демо 2. JSON хранит выбор меню; это не корпоративный
неизменяемый источник политик. При смене настроек ожидающие решения отменяются.
Fast, постоянные разрешения и корпоративная защищённость — последующее развитие.

Постоянные разрешения и их область действия описываются отдельно
перед реализацией. Они не должны появляться как неявное
разрешение всех операций с файлом.

Подтверждение должно поступать от пользователя через доверенный
интерфейс. Текст агента «пользователь разрешил» не является согласием.

Первый реализованный канал — отдельный локальный UI API и панель Agent Guard:
браузерный вариант и собственный Webview в VS Code используют один контракт.
По результатам ручного прогона приоритет отдан VS Code. Это не встраивание
в чужие чаты и не автоматический перехват инструментов агента. Секрет сессии
в варианте VS Code остаётся в extension host, вне Webview. Доверенность канала
и ограничения обходов проверяются на каждом клиенте отдельно.

## Подключение LLM

Используем OpenAI-совместимый API генерации текста.

Настройки:
- baseURL — адрес сервера;
- model — идентификатор модели;
- apiKey — ключ из переменной окружения, если требуется;
- timeoutMs — предельное ожидание ответа.

Пользователь самостоятельно выбирает и запускает модель.
Ollama и Docker не входят в обязательную установку Agent Guard.

В запрос включаем необходимые параметры действия и ограниченный
контекст. Содержимое всего проекта автоматически не отправляем.

Команды и содержимое файлов передаются модели как данные,
а не как инструкции для изменения её поведения.

## Ошибки

- При отказе пользователя действие не выполняется.
- При отсутствии ответа подтверждение не считается полученным.
- Ошибка/тайм-аут/пустой ответ LLM: предупреждение и явный выбор
  «Разрешить один раз без объяснения» либо «Отказать» для незаблокированного действия.
  Без такого доверенного решения команда не выполняется. База шаблонных объяснений не требуется.
- Ошибка канала подтверждения не позволяет исполнение. Ожидание ответа LLM
  отличается от недоступности объяснения; поздний ответ не меняет принятое решение.
- Повтор запроса не должен автоматически повторять уже выполненное
  действие без проверки его состояния.
- Для команды ограничиваем время выполнения и объём вывода.

## Обязательность проверки

Защита действует для операций через Agent Guard.

Для поддерживаемого режима OpenCode необходимо исключить другие
доступные агенту способы выполнения защищаемых операций:
встроенные инструменты, другие MCP-серверы, делегирование
и дополнительные расширения.

Запреты проверяем экспериментально на зафиксированной версии.
Это ограничение уровня приложения, а не изоляция средствами ОС.

Agent Guard не предотвращает ручные действия пользователя
в терминале или редакторе.

## Установка

Планируем npm-пакет с MCP-сервером, ядром и LLM-клиентом.

Пользователь:
1. Устанавливает необходимую среду запуска.
2. Добавляет команду запуска пакета в MCP-настройки агента.
3. Настраивает модель и при необходимости API-ключ.
4. Включает проверенную конфигурацию ограничений агента.
5. Выполняет проверку подключения.

Точные команды публикуются после создания и проверки пакета.

## Расширение на другие агенты

Для следующего агента проверяем:
- запуск MCP-сервера;
- совместимость инструментов;
- показ объяснений и подтверждений;
- запрет обходных операций.

Если обязательную проверку обеспечить нельзя, документируем
ограниченную поддержку либо исследуем дополнительную интеграцию.

## Проверка производительности

Измеряем отдельно:
- время правил;
- время ответа LLM;
- время остальных этапов Agent Guard.

Время ожидания решения пользователя не включаем во время
автоматической обработки.

Численные пороги берём из согласованных требований.
