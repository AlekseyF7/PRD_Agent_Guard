# Требования Agent Guard

**Версия:** 2

## 1. Назначение продукта

Agent Guard — инструмент безопасности и осознанного контроля кодинговых ИИ-агентов. Система проверяет потенциально опасные действия до их выполнения, объясняет пользователю возможные последствия и позволяет принять решение о выполнении действия.

Целевая аудитория — студенты, начинающие разработчики и другие пользователи кодинговых агентов, которым сложно самостоятельно оценивать риски технических действий. Для опытных пользователей продукт должен обеспечивать дополнительный контроль без избыточных уведомлений.

Основная задача — сохранить преимущества автоматизации, снизив риск нежелательных изменений в проекте и окружении пользователя.


## 2. Пользовательские требования

- Перед решением пользователь должен понимать, что агент собирается сделать, какие ресурсы затронет и чего ожидать после выполнения. Если затрагиваемый ресурс или последствия неизвестны, пользователь должен видеть эту неопределённость. 
- Пользователь должен уметь остановить рискованное действие и при необходимости уточнить последствия, пока оно ожидает решения. Для привычных операций нужен минимум повторных запросов.
- Пользователю нужна возможность выбирать доступную глубину объяснения. Короткая калибровка остаётся гипотезой развития.

- **P1** — развитие после Демо 2
- **P2** — дальнейшее развитие.

## 4. Основной пользовательский сценарий

1. Пользователь подключает Agent Guard и работает с ИИ-агентом.
2. Агент инициирует поддерживаемое действие, которое поступает на проверку до выполнения.
3. Agent Guard оценивает риск и определяет допустимость действия.
4. Если требуется подтверждение, система формирует объяснение через LLM, показывает действие и возможные последствия.
5. Пользователь разрешает действие один раз или отказывает.
6. Система выполняет разрешённое действие либо блокирует его и возвращает результат агенту.

В развитом MVP действия, однозначно разрешённые политикой, не требуют дополнительного подтверждения; запрещённые действия блокируются независимо от ответа LLM. В первой версии при ошибке объяснения действие не выполняется.

## 5. Нефункциональные требования

- **Понятность и точность.** Объяснение понятным языком раскрывает существенные риски. На тестовом запросе описание действия и последствий сверяется с известным эффектом команды. При пользовательской проверке попросить новичка своими словами назвать действие, затронутый объект и последствие.
- **Задержка.** На готовой сборке по 007 выполнить минимум 10 безопасных запросов объяснения. Отдельно измерить время LLM и всей автоматической проверки, исключив ожидание решения и выполнение команды. Зафиксировать медиану, максимум и ошибки. Допустимый порог пока не согласован. 
- **Частота предупреждений.** Для MVP измерять долю ложных срабатываний на эталонных безопасных сессиях по цели PRD из раздела 1. На Демо 2 проверить, что разрешённое чтение остаётся доступным. 
- **Конфиденциальность.** Во внешнюю LLM передаётся необходимый разрешённый контекст. На тестовых данных сверить исходящий запрос с согласованным перечнем полей, а логи и конфигурацию для распространения проверить на отсутствие ключей. Допустимый состав облачного контекста пока не согласован. 

## 6. Правила безопасности

По плану команды защищаются поддерживаемые операции на конкретной проверенной версии и конфигурации агента. Обнаруженный обход ограничивает заявленный объём защиты.

- **Неизменность действия (FR-05, FR-06).** Согласие относится к показанной команде с зафиксированными параметрами и рабочей папкой. Изменение или повторный вызов требуют нового решения.
- **Доверенное согласие (FR-05).** Разрешение поступает непосредственно от пользователя через доверенный интерфейс. Запрет правил действует независимо от ответа LLM или агента.
- **Безопасный отказ (FR-07).** При ошибке проверки или подтверждения, отсутствии согласия, ошибке или тайм-ауте LLM действие остаётся невыполненным. Причина отказа возвращается пользователю или агенту.
