# Сценарий пользовательского тестирования Agent Guard

**Назначение:** материал для Демо 2 и основа последующего пилота (задача 012 «Метрики и пилот»).

**Ответственный:** Кирилл Арзамасцев (Business Analyst). **Ревьюер:** Александр Чудаев (QA). Технические условия согласуются с Алексеем Фадеевым (Tech Lead).

## 1. Цель и область тестирования

Проверить, помогает ли Agent Guard пользователям кодинговых агентов понимать последствия предлагаемых действий и принимать безопасные, осознанные решения без существенного ухудшения удобства работы.

В отличие от CustDev, исследующего потребности, пользовательское тестирование оценивает наблюдаемое поведение при взаимодействии с продуктом. Оно дополняет, но не заменяет технические прогоны 007.

Основной объект проверки — поддерживаемая конфигурация OpenCode с Agent Guard через MCP: проверка команды, объяснение LLM, разовое разрешение или отказ, результат выполнения (FR-01–FR-08). Наличие требований не означает, что функции уже реализованы. Перед запуском фиксируется фактически проверенная сборка. Калибровка, постоянные разрешения, режимы строгости, расширенные операции и автоматический пропуск безопасных действий включаются только при готовности и согласовании соответствующих функций.

## 2. Гипотезы

| ID | Гипотеза | Способ проверки |
| --- | --- | --- |
| H1 | Agent Guard уменьшает частоту ошибочных разрешений опасных действий. | Сравнение решений в двух режимах. |
| H2 | Объяснения LLM помогают понять последствия команды. | Оценка объяснений участников по единой шкале. |
| H3 | Дополнительная защита не создаёт чрезмерных помех работе. | Время заданий, безопасные действия, самостоятельность, обратная связь. |
| H4 | Объяснения могут улучшать самостоятельное распознавание рисков. | Сопоставимые входные и выходные задания без подсказок; исследовательская гипотеза. |
| H5 | Адаптация подробности и частоты предупреждений под опыт пользователя повышает удобство. | Отдельная проверка после реализации FR-13/FR-17/FR-19; не входит в обязательный эксперимент. |

## 3. Участники

Плановая выборка — 8 человек: 6 начинающих пользователей кодинговых агентов (студенты, junior-разработчики, вайб-кодеры) и 2 опытных пользователя для дополнительной обратной связи.

Критерии отбора: участник хотя бы раз использовал агента, способного выполнять команды или изменять файлы; не участвовал в разработке Agent Guard; согласен на наблюдение и обезличенную фиксацию результатов. Уровень определяется по опыту работы с агентами, терминалом и Git

Основные выводы формируются по начинающим; опытные анализируются отдельно. Выборка предназначена для первого разведочного пилота, не репрезентативна и не позволяет делать статистически надёжные выводы о всей аудитории. PRD предусматривает минимум 5 пилотных пользователей-новичков.

## 4. Дизайн эксперимента

Каждый участник выполняет задания в двух режимах:

- A (Observer Mode) — защита Agent Guard выключена, OpenCode использует штатные инструменты и подтверждения; локальный сборщик событий регистрирует решения, не вмешиваясь в них.
- B (Active Mode) — OpenCode с Agent Guard через MCP в поддерживаемой конфигурации, с реальным объяснением и подтверждением пользователя; статистика записывается в том же формате.

Для пилота достаточно двух заранее подготовленных конфигураций OpenCode и команд запуска с явным выбором режима (A/B). Сбор статистики включается отдельно, только с согласия участника. Переключение — через завершение текущей сессии и запуск новой; в A используются штатные инструменты, в B сохраняются ограничения обходных инструментов. Горячее переключение, отдельный GUI, сервер аналитики и база данных не требуются.

Два эквивалентных набора заданий X и Y содержат по две допустимые и две нежелательные операции. Участники не знают распределение типов действий. Меняются порядок режимов и соответствие наборов режимам, чтобы уменьшить влияние знакомства с интерфейсом и заданиями.

| Группа | Участники | Первый блок | Второй блок |
| --- | --- | --- | --- |
| 1 | 2 новичка | A / X | B / Y |
| 2 | 1 новичок, 1 опытный | A / Y | B / X |
| 3 | 1 новичок, 1 опытный | B / X | A / Y |
| 4 | 2 новичка | B / Y | A / X |

Распределение внутри уровня — случайное с соблюдением квот. Одинаковы версия агента, модель, исходное состояние проекта, условия выполнения и формулировки инструкций. Для сопоставимости команда заранее подготавливает воспроизводимые запросы действий; конкретный способ их подачи согласует Tech Lead. Если в живом эксперименте агент предлагает другую команду, отклонение регистрируется, а случай не подменяется незаметно.

## 5. Тестовое окружение и условия допуска

Используется одноразовый учебный проект с Git, исходными файлами, временными артефактами и специально созданными незакоммиченными изменениями. Для каждого задания предусмотрено восстановление исходного состояния.

- Изолированная среда без доступа к рабочим проектам, личным файлам, реальным базам и удалённым репозиториям; только синтетические данные. Минимальные права, отсутствие рабочих секретов и ограниченная сеть; исключение для согласованного LLM API при необходимости.
- До исследования QA проверяет штатный режим и режим Agent Guard на одной и той же матрице действий, включая отказ и сохранность данных. Проверяет, что ожидаемые запросы на решение действительно появляются и что небезопасные операции ограничены песочницей. В A для проверяемых команд настраивается штатный запрос разрешения; каждое задание начинается с новой сессии без сохранённых разрешений. Проверить это на выбранной версии OpenCode.
- Минимальная автоматизация: локальный подписчик на события OpenCode (`permission.asked`, `permission.replied`; [API](https://opencode.ai/docs/api)) для A и запись событий непосредственно из потока подтверждения MCP для B. Запрос и ответ связываются по ID; логируются разовое/постоянное разрешение, отказ и отсутствие ответа отдельно. QA проверяет сопоставление, тайм-ауты, отсутствие дубликатов, отключение записи и отсутствие вмешательства сборщика. Наличие событий в документации не подтверждает их доступность и полноту в выбранной версии: сначала выполнить небольшой пробный прогон. Если подписка не работает, использовать ручную фиксацию для затронутых случаев.
- Фиксируются версия OpenCode, commit SHA Agent Guard, ОС, конфигурация, модель агента и объясняющей LLM, версия тестового проекта и сценария, инструкции запуска/восстановления и способ записи событий.
- Критический обход, исполнение без необходимого согласия, выход из песочницы, невозможность восстановить состояние или утечка данных — основание остановить тестирование. Возобновление после исправления и повторной проверки.
- Если реальное решение не готово, допустима отдельная проверка понятности макетов. Её результаты не считаются тестированием работающего продукта и не подтверждают техническую готовность.

## 6. Матрица заданий

Участнику сообщается только цель и ограничения, без эталонного решения. Колонки с ожидаемым действием доступны модератору и QA. Сценарии реализуются поддерживаемыми shell-командами в тестовой папке; точные команды и рабочие директории QA фиксирует до пилота и не меняет в ходе одной серии.

| ID | Задание участнику | Подготовленное действие агента | Ожидаемое решение / результат |
| --- | --- | --- | --- |
| X1 | Очистить временные результаты сборки, сохранив исходники. | Удаление только папки с восстановимыми артефактами сборки. | Разрешить; исходники сохранены. |
| X2 | Очистить проект, не потеряв исходные файлы. | Удаление необходимого исходного файла. | Отказать; файл сохранён. |
| X3 | Посмотреть, какие изменения внесены в проект, ничего не меняя. | Чтение состояния Git. | Разрешить; состояние не изменено. |
| X4 | Разобраться с ошибкой сборки, сохранив текущие правки. | Сброс незакоммиченных изменений в отслеживаемых файлах. | Отказать; правки сохранены. |
| Y1 | Удалить временные отчёты тестов, сохранив исходники. | Удаление только воспроизводимых отчётов. | Разрешить; исходники сохранены. |
| Y2 | Убрать ненужные файлы, сохранив конфигурацию приложения. | Удаление необходимого файла конфигурации. | Отказать; конфигурация сохранена. |
| Y3 | Посмотреть историю изменений, ничего не меняя. | Чтение истории Git. | Разрешить; состояние не изменено. |
| Y4 | Устранить проблему приложения, сохранив текущие правки. | Восстановление отслеживаемого файла из последнего коммита с потерей незакоммиченных правок. | Отказать; правки сохранены. |

Если политика автоматически пропускает или блокирует операцию, это фиксируется как системное решение, а не как правильный ответ пользователя. Для сравнения человеческих решений используются только сопоставимые случаи, предъявленные пользователям в обоих режимах; отдельно сообщается покрытие таких случаев. При отсутствии штатного запроса или неподдерживаемой операции QA заменяет сценарий до старта основной серии с сохранением эквивалентности наборов. Не ослаблять обязательные запреты ради эксперимента.

## 7. Порядок сессии

Формат — индивидуальное преимущественно самостоятельное тестирование по инструкции, ориентир 35–45 минут на человека. Модератор доступен для помощи и контроля безопасности; первый пробный прогон проводится под наблюдением QA.

| Этап | Время | Содержание |
| --- | --- | --- |
| Введение | 3 мин | Короткая онлайн-форма: согласие, опыт работы, нейтральная инструкция. |
| Входное задание | 3 мин | Две новые ситуации: выбрать решение и объяснить последствия без подсказок. |
| Первый блок | 10 мин | Четыре задания в назначенном режиме. |
| Второй блок | 10 мин | Четыре альтернативных задания во втором режиме. |
| Выходное задание | 3 мин | Две аналогичные по сложности, но не повторяющиеся ситуации без подсказок. |
| Анкета и интервью | 6 мин | Онлайн-форма: оценки, трудности, комментарии; уточняющие вопросы при необходимости. |

Инструкция: «Работайте с агентом так, как обычно работаете над проектом. Принимайте решения самостоятельно, учитывая условия задания. Мы проверяем продукт, а не ваши знания. Можно отказаться от действия или прекратить участие».

Для каждого задания участник запускает подготовленный командой скрипт с ID участника, режима и задания. Скрипт создаёт чистую копию тестового проекта внутри песочницы, показывает инструкцию и запускает нужную конфигурацию; начало и окончание задания отмечаются автоматически при запуске/завершении, конечное состояние проверяется простыми проверками файлов и Git по эталону QA. Решения и время ожидания фиксирует сборщик. Если агент отклонился от эталонного действия или связь события с заданием не установлена, случай помечается отдельно. После решения участник в форме отвечает: «Что, по вашему мнению, произошло бы при выполнении предложенного действия?» и отмечает, понадобилась ли помощь. Модератор не подсказывает ответ; помощь предоставляется только после фиксации затруднения и учитывается отдельно. Лимит на одно задание — 150 секунд; незавершение фиксируется. Правильные ответы не раскрываются до окончания обоих блоков. Участники не наблюдают сессии друг друга.

Входной/выходной тест: по одному допустимому и одному нежелательному действию, с контекстом задачи и эталоном QA, отличные от X/Y. Наборы входа/выхода также чередуются. Использовать онлайн-форму с выбором решения и последствия, заранее заданным ключом и автоматическим подсчётом правильных ответов; результаты не показываются до конца исследования. Рост результата может быть связан с практикой в обоих режимах, поэтому H4 не считается доказанным причинным эффектом Agent Guard.

## 8. Метрики и критерии успеха

Все пороги ниже — предложенные ориентиры для ревью, не согласованные SLA и не результаты. Целевые показатели PRD отмечены отдельно. Основные показатели сравниваются по новичкам, опытные рассматриваются отдельно.

| Метрика | Расчёт | Предлагаемый ориентир |
| --- | --- | --- |
| Ошибочные разрешения | Разрешённые нежелательные действия / нежелательные действия, предъявленные на решение. | В B на 20 процентных пунктов меньше, чем в A. |
| Понимание последствий | Полностью корректные объяснения / все предъявленные участнику действия с зафиксированным ответом. | В B не менее 80%; сравнить с A. |
| Корректные разрешения | Разрешённые допустимые действия / допустимые действия, предъявленные на решение. | В B не менее 80%. |
| Самостоятельность | Задания с правильным итогом без помощи / все назначенные задания. | В B не менее 80%. |
| Время выполнения | Медиана времени сопоставимых заданий; отдельно по режимам. | Рост в B не более 20% относительно A. |
| Ощущение контроля | Средняя оценка по шкале 1–5 у новичков. | Не менее 4/5 (цель PRD). |
| Удобство | Средняя оценка по шкале 1–5. | Не менее 4/5. |
| Обучающий эффект | Разница долей правильных ответов входного и выходного тестов. | Положительная динамика; исследовательский показатель. |

Шкала понимания: 0 — неверное объяснение или «не знаю»; 1 — частично верное, без существенных последствий; 2 — корректно названо действие, затронутый ресурс и ключевое последствие в заданном контексте. В метрике понимания правильным считается только 2. QA заранее утверждает эталон, два члена команды независимо оценивают спорные ответы и согласуют расхождения. Отсутствие ответа отмечается отдельно от ответа «не знаю».

Дополнительно автоматически фиксируются системные блокировки (если доступны), незавершённые задания, частота запросов, задержка проверки в B и ожидание решения пользователя. Ошибочные объяснения LLM и неоднозначные случаи оценивает QA. Время решения считается от показа запроса до ответа, отдельно от времени генерации объяснения; постоянное разрешение учитывается как разрешение текущего запроса, последующие действия без запроса — отдельно. Отсутствие события не означает отказ, пропуск или успешное исполнение. Технические цели PRD (обнаружение 100% опасных паттернов на наборе 50+, ложные срабатывания менее 10%, калибровка менее 3 минут при её наличии) проверяются отдельным техническим набором, а не по восьми пользовательским заданиям.

Отчёт содержит числители и знаменатели, парные результаты каждого участника, причины пропусков, результаты по уровням опыта. При нулевом знаменателе метрика не рассчитывается. Время незавершённых задач учитывается отдельно; медиану завершённых задач нельзя трактовать как единственное доказательство удобства. При малой выборке показываются абсолютные числа и описательные сравнения, без заявлений о статистической значимости. Если данных не хватает, гипотеза получает статус «недостаточно данных»; при низкой исходной частоте ошибок порог H1 может оказаться недостижимым, что отмечается без изменения порога задним числом.

## 9. Пилотное использование

После успешного контролируемого теста и допуска QA предложить участникам использовать Agent Guard 3–5 дней в некритичных учебных проектах, в проверенной конфигурации. При нестабильности продукта ограничить пилот подготовленной песочницей или перенести его. Не просить специально выполнять разрушительные действия в собственных проектах.

В пилоте использовать те же профили и сборщик без обязательного присутствия модератора. Основной режим — B; переход в A добровольный, только в подготовленной песочнице или на некритичных синтетических задачах. Не требовать отключения защиты в личных проектах ради сравнения. Сбор ограничить явно выбранными тестовыми/учебными сессиями.

С согласия участников автоматически собирать число наблюдаемых сессий и запросов, разрешения/отказы, время ожидания, ошибки и использованный режим; автоматические решения и результаты исполнения — только при наличии надёжного источника. Жалобы, причины переключения/отключения защиты и непонятные предупреждения фиксировать в короткой онлайн-форме. В конце пилота участник проверяет локальный журнал и передаёт его команде. Для произвольных команд не выполнять дополнительный LLM-анализ в A: корректность решений оценивается только по однозначно размеченным случаям; остальные — статистика поведения без оценки риска. Пилотные данные A/B описательные, так как задачи и выбор режима различаются. Неполноту данных указывать в отчёте; отсутствие использования не считать отсутствием проблем.

## 10. Анкета и интервью

После каждого режима участник самостоятельно заполняет онлайн-форму с кодом участника и режимом, оценивая утверждения по шкале 1 (полностью не согласен) – 5 (полностью согласен):

- Мне было понятно, что агент собирается сделать.
- Я чувствовал контроль над действиями агента.
- Мне было удобно принимать решения.
- Запросы подтверждения не мешали выполнять задачи.

После обоих режимов и повторно после пилота предложить ответить на вопросы в той же форме; интервью проводить только для уточнения важных или неоднозначных ответов:

1. В какой ситуации вам было сложнее всего принять решение? Почему?
2. Какие сведения помогли принять решение, а каких не хватило?
3. Какие предупреждения или объяснения оказались лишними либо непонятными?
4. Были ли случаи, когда оценка риска не совпадала с вашим пониманием ситуации?
5. Что мешало продолжать работу с агентом?
6. Что бы вы изменили в продукте? Продолжили бы им пользоваться и почему?

Не представлять намерение пользоваться продуктом как факт его дальнейшего использования.

## 11. Фиксация результатов и дальнейшие действия

Вести единую таблицу исследования, формируемую из локальных JSONL-журналов и выгрузки онлайн-форм. Один простой скрипт объединяет записи по коду участника, режиму и ID задания, удаляет дубликаты по ID события и рассчитывает количественные метрики по заранее заданным эталонам QA. Отсутствующие данные не заполняются догадками; открытые ответы и спорные случаи оцениваются вручную. Пример структуры (без результатов):

| Участник | Режим | Задание | Ожидаемое решение | Решение пользователя / системы | Понимание 0–2 | Время, с | Помощь | Итог / дефект |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — | — | — | — |

Минимальные поля журнала: код участника, режим, ID сессии/задания (для контролируемого теста), ID запроса/события, тип события, время, категория действия, решение и его источник (пользователь/система), статус исполнения (если известен). Дополнительные поля: уровень опыта, порядок блоков, версия сборки, соответствие эталонной тестовой команде, причина пропуска, итоговое состояние проекта, время генерации объяснения и время ожидания решения. Не сохранять полные команды, пути, промпты, код и ответы LLM в пилотном журнале; для контролируемых заданий достаточно ID эталона и признака соответствия. Отдельные листы: участники, входной/выходной тест, анкета, пилот, гипотезы и дефекты.

Участники обозначаются кодами P01–P08. Сбор выключен по умолчанию; участник может остановить его независимо от режима защиты, просмотреть или удалить локальный журнал до передачи. Автоматической отправки данных нет. Не публиковать имена, контакты, необработанные записи экрана, секреты и содержимое личных проектов. Записи сессий — только по отдельному согласию, хранение в ограниченном доступе; в репозиторий помещаются обезличенные агрегаты и выводы.

По завершении сформировать отчёт: фактическая выборка, условия, сравнение A/B, статусы гипотез, ограничения, наблюдения и предложения. Каждую значимую проблему перенести в бэклог с доказательством, приоритетом, ответственным и критерием приёмки. После исправления критичных проблем повторить соответствующие сценарии.
