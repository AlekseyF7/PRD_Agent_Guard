# Реализация и проверка MCP/исполнения 006

Дата: 27.11.2026. Ветка: feature/aleksey/006-mcp-execution.
Основание: [006](../../specs/006-mcp-execution.md),
[контракт 003](../../specs/003-contract-and-core.md),
[LLM-клиент 005](../../specs/005-llm-client.md).
Это отчёт о реализации и самопроверке; независимая приёмка ещё требуется.

## Что реализовано

- src/mcp — stdio MCP на официальном SDK, единственный инструмент guard_execute_command,
  конфигурация, соединение компонентов и служебная запись для открытия панели.
- src/execution — состояния попытки, проверка согласия, контроль изменения целей,
  исполнение, лимиты, отмена и отдельный ограниченный анализ PowerShell.
- src/approval — браузерная карточка, одноразовый nonce решения, локальный HTTP API
  с секретом сессии и проверками Host/Origin. Команды, риски, объяснение и вывод
  отображаются как текст; поля агента не становятся HTML/скриптом.
- scripts/check-guard.mjs — настоящий MCP-клиент для безопасного ручного прогона.
- scripts/open-panel.mjs — локальный запуск браузера пользователем.
- examples/mcp — примеры конфигурации сервера и кандидат конфигурации OpenCode.
- tests/execution.test.ts, tests/mcp.test.ts — новые проверки.
- В 003 добавлены исходная command в контексте правила и доверенная подстановка
  parser; формат запроса агента не расширяется. По умолчанию старый POSIX-профиль
  не меняется. Для Windows он не применяется к синтаксису PowerShell.

MCP SDK 1.32.2 и Zod 4.6.7 зафиксированы в lock-файле. npm install выполнен
с --ignore-scripts. Среда самопроверки: macOS, Node.js v24.21.0.

Профиль исполнения фиксируется сервером по ОС и показывается в карточке:
macOS — /bin/sh -c, Windows — штатный Windows PowerShell без профиля, с точным
UTF-16LE/Base64 EncodedCommand. Команда из MCP не может выбрать другую оболочку.
Ключи LLM не наследуются окружением команды; известные серверу секреты дополнительно
маскируются в выводе. Это не универсальный поиск секретов и не OS-песочница.

Лимиты по умолчанию: исполнение 120000 мс, ожидание человека 120000 мс,
stdout и stderr по 65536 байт. Тайм-аут LLM задаётся отдельно.
В первом объёме одна активная попытка на процесс сервера; другая получает BUSY.
После Демо 2 пересмотреть очередь и несколько сессий. Изменение настроек через
внутренний replace отменяет старую попытку; полноценное пользовательское меню
изменения настроек относится к 004 и здесь ещё не реализовано.

## Самопроверка и критерии 006

Команды: npm run check; npm test; git diff --check.
Loopback-тесты требуют разрешения открыть временный локальный сервер.
Все исполняемые сценарии используют специально созданные временные папки;
рабочие файлы, базы, реальные удалённые репозитории и облачные ключи не используются.

| Критерий / сценарий | Ожидание | Фактический результат |
|---|---|---|
| 1. Старт и каталог MCP | Только guard_execute_command, строгие command/cwd | Проверено SDK-клиентом, в памяти и через отдельный stdio-процесс. approved отклоняется до попытки |
| 2. Объяснение и ожидание | Процесс не запускается до решения | Проверено с управляемым API; файл сохраняется во время ожидания. Ручной прогон Алексея с подготовленной конфигурацией получил объяснение; независимое повторение ещё требуется |
| 3. Block/отказ/ошибки | Запрет пропускает LLM/UI; отказ и отсутствие решения не исполняют | Проверено, включая ошибку/тайм-аут ожидания, отмену и ошибку объяснения |
| 3. Недоступное объяснение | Только явное allow_once_without_explanation | Обычное allow_once отвергается; отдельное разрешение запускает ровно одну попытку |
| 4. Разовое исполнение | Именно показанная команда в показанной папке | Через MCP + HTTP UI API отказ сохранил синтетический sample.txt, новый вызов с разрешением удалил его |
| 5. Повтор и подмена | Старое/чужое/повторное согласие не подходит | Проверены UUID, nonce, два сообщения, новые попытки и замена конфигурации |
| 5. Изменение файлов | Новое состояние требует новой проверки | Изменение известного файла после объяснения даёт STALE_ACTION без запуска |
| 6. Лимиты/ошибки процесса | Ограниченное накопление, отдельные ошибки | Проверены stdout cap, ненулевой exit, плохой cwd, timeout и cancel |
| 6. Потомки | Timeout останавливает дочерний процесс | На macOS потомок не записал отложенный маркер после остановки группы; Windows taskkill ещё не проверен |
| 7. Разрыв до старта | Исполнения нет | Проверен внешний AbortSignal и отмена ожидающего UI. Произвольный сбой ОС не моделируется как гарантированно безопасный |
| 8. Реальная интеграция и ревью | Воспроизводимый проход другим человеком | Алексей выполнил ручные разрешение/отказ через браузер и сообщил об успешной проверке панели VS Code; реальные агенты, Windows и независимая приёмка критериев ещё требуются |
| UI-канал | Только с секретом сессии, правильными Host/Origin и nonce | Проверено HTTP-тестами. Неверный Host проверяется node:http, поскольку fetch нормализует Host |
| Секреты | Нет URL/секрета панели в MCP-ответе и stdout старта | Проверено; известный секрет маскируется в результате одобренной тестовой команды |
| Windows | Настоящее исполнение и дерево процессов | Не проверено. На macOS проверены только разбор, построение аргументов и кодирование команды |

Итоговая серия: **192 теста, 192 успешных, 0 ошибок/пропусков** на macOS:
156 прежних проверок и 36 проверок исполнения/MCP/UI. `npm run check` и
`git diff --check` проходят. Проверена конфигурация с UTF-8 BOM и маскирование
секрета в результате разрешённой команды. Это не факт прохождения Windows
или настоящего агента.

Инструмент браузера был недоступен. Позднее Алексей самостоятельно выполнил
браузерный прогон и передал скриншоты: разрешение и отказ сработали, но обнаружены
дефекты отображения и жизненного цикла проверочного клиента. Их исправления
и перенос панели в VS Code описаны ниже. Последующая обратная связь Алексея
о ручной проверке приведена в разделе оформления ниже. Windows ещё требует
ручного прогона; DOM и mock extension host его не заменяют.

## Самый быстрый ручной прогон на Mac

1. Из корня репозитория установить зависимости и собрать:

```sh
npm ci --ignore-scripts
npm run build
```

2. Создать отдельную тестовую папку, например /private/tmp/agent-guard-demo-006/project.
Скопировать [guard-config.json](../../examples/mcp/guard-config.json) в отдельный
локальный файл, например /private/tmp/agent-guard-demo-006/guard.json. Заменить
workspaceRoot на существующий абсолютный путь тестовой папки. Это файл настроек,
не пример внутри репозитория. Ключ в JSON не вводить.

3. Для Groq ввести ключ в этом же терминале скрытым вводом:

```sh
read -rs 'AGENT_GUARD_LLM_API_KEY?Ключ Groq (ввод скрыт): '
printf '\n'
export AGENT_GUARD_LLM_API_KEY
npm run guard:check -- /private/tmp/agent-guard-demo-006/guard.json
```

Скрипт запускает MCP-сервер и отправляет только безопасную команду вывода
строки guard-check. В первом терминале появится PID и команда открытия панели.
Не вводить JSON руками в stdin MCP и не запускать произвольные команды в этом процессе.

4. Для браузерного запасного интерфейса во втором терминале из корня проекта
выполнить напечатанную команду. Основной интерфейс теперь — расширение VS Code,
см. раздел ниже; оно обнаруживает сервер и открывает панель без этой команды:

```sh
npm run guard:panel -- PID_ИЗ_ПЕРВОГО_ТЕРМИНАЛА
```

Браузер открывается по частной ссылке из служебного каталога пользователя.
Секрет не печатается в терминал и не возвращается агенту. Если открыто несколько
серверов, выбрать именно нужный PID. Карточка покажет команду, cwd, оболочку,
известные риски и объяснение. Сначала выбрать «Отказать»: исполнение отсутствует.
Нажать Enter в первом терминале для новой попытки в той же панели
и выбрать «Разрешить один раз»:
ожидается stdout с guard-check и exitCode=0. Повторное сообщение не исполняет ещё раз.
Теперь guard:check сохраняет сервер после результата. Нажать Enter в первом
терминале для новой безопасной попытки в той же панели либо q для завершения.
Ctrl+C также отменяет активную попытку и завершает сессию. Для однократного
автоматического запуска существует --once. Согласие не выдаётся клавишей Enter:
она создаёт новый запрос, который опять ждёт отдельного решения в UI.
Закрытие панели до решения отменяет попытку через запрос закрытия либо после
пропадания heartbeat; если ни один запрос панели не поступил, действует тайм-аут.

5. После завершения в первом терминале:

```sh
unset AGENT_GUARD_LLM_API_KEY
```

Источник ключа пока env. Системное хранилище, меню политик и LLM — ещё работа 004.
Если ключа нет или модель недоступна, панель показывает предупреждение и отдельное
«Разрешить один раз без объяснения». Это проверка деградированного сценария,
не доказательство подключения модели. LLM-клиент 005 проверен ранее отдельно.

## Windows 11: прогон Алексея или Александра

Node.js 24 и npm нужны; Git Bash и Ollama не обязательны. В существующем
терминале PowerShell выполнить npm ci --ignore-scripts и npm run build.

Подготовить тестовую папку и конфигурацию с её абсолютным Windows-путём.
В JSON обратные слеши экранируются: C:\\path\\project. Конфигурация допускает
UTF-8 BOM, который может записать Windows PowerShell. Для Qwen в LM Studio
использовать [локальный пример](../../examples/mcp/guard-config-local.json),
указать фактический порт/model ID, запустить API-сервер. При none убрать
credentialRef: облачный ключ локальному серверу не передаётся.

Для Groq ключ можно ввести в PowerShell без отображения и записи в командную историю:

```powershell
$guardSecret = Read-Host 'Ключ Groq' -AsSecureString
$env:AGENT_GUARD_LLM_API_KEY = [System.Net.NetworkCredential]::new('', $guardSecret).Password
Remove-Variable guardSecret
npm run guard:check -- 'C:\path\guard.json'
Remove-Item Env:AGENT_GUARD_LLM_API_KEY
```

Источник env требует расшифрованного значения в памяти процесса; SecureString
не означает, что весь дальнейший процесс работает с зашифрованным ключом.
Второй терминал: npm run guard:panel -- PID. Это не выполнение команды
Remove-Item над файлом: последняя строка выше удаляет только переменную окружения.

Проверить и приложить к отчёту:

- Windows/Node/PowerShell версии, commit SHA, агент/сервер и model ID;
- npm run check и npm test (POSIX-специфичный тест остановки группы может быть skipped);
- отказ и разрешение для guard-check, правильность cwd и профиля windows-powershell;
- отдельные синтетические сценарии Remove-Item, блокировка file_delete,
  отмена/тайм-аут, остановка дочернего процесса, усечение stdout/stderr;
- вывод кириллицы и UTF-8: корректность пока не подтверждена;
- факт/ожидание, коды результата, сохранность тестовых файлов и ограничения.

Сначала работать на временных данных. Выход за тестовое дерево, исполнение без
согласия или продолжающий работу процесс после отмены — дефекты, которые нельзя
объявлять успешной проверкой. Прогон Windows на macOS не имитируется как реальный.

## Подключение к агенту — отдельная проверка

MCP-клиент запускает Node напрямую, без npm run (служебные строки npm в stdout
повредят протокол). Команда сервера: node ABSOLUTE/dist/src/mcp/main.js ABSOLUTE/config.json.
Пример для OpenCode v2.4.2: [opencode-006.json](../../examples/mcp/opencode-006.json).
Нужно заменить все пути. Это кандидат, основанный на профиле исследования 001;
новая связка пока не прошла реальный OpenCode-прогон.

Протокольное имя инструмента — guard_execute_command. OpenCode может добавлять
имя сервера guard: ожидаемое имя guard_guard_execute_command нужно сверить
с фактическим каталогом. Пример разрешает только его, без встроенного shell,
редактирования, чтения и остальных инструментов. Это узкий профиль проверки,
не полная конфигурация 004 с разрешённым чтением проекта. Не включать дополнительные
инструменты до проверки обходов и чтения служебных файлов панели.

Тайм-аут MCP-клиента должен покрывать LLM + решение человека + исполнение + запас.
В примере execution=600000; работоспособность параметров на версии клиента
подтверждается отдельным опытом, не наличием JSON. При ранней отмене со стороны
клиента сервер не должен исполнить старое согласие. Не менять глобальные настройки
агента ради исследования — использовать отдельный синтетический проект.

Codex и GigaCode в VS Code — следующие кандидаты. Общий MCP-сервер не доказывает
запрет встроенных инструментов или поддержку UI на этих клиентах. Перед пилотом
нужны версия, каталог, вызов, подтверждение и проверка обходных путей.

## Границы защиты

Loopback, отдельный случайный секрет, Host/Origin, nonce и запрет вывода секрета
разделяют UI и MCP на уровне приложения. Служебная запись хранится вне workspace
в ~/.config/agent-guard/instances (macOS) или LOCALAPPDATA/AgentGuard/instances
(Windows); POSIX-права ограничены при создании. Это не корпоративная защита
от кода с правами того же пользователя. AGENT_GUARD_STATE_DIR — доверенная
настройка запуска для тестов; не помещать служебные записи в доступное агенту дерево.

Настройки 004 и ограничения обходных инструментов клиента обязательны для
вывода о защищённой интеграции. Произвольная команда может читать/менять данные
вне cwd, известные цели неполны. Оболочка и процессы не изолированы средствами ОС.
Снимок/отпечатки не исключают все гонки. Демоны и фоновые задачи не поддерживаются;
после сбоя автоматического повтора нет. При неизвестном исходе не заявлять откат.
При отмене во время объяснения уже отправленный запрос LLM может продолжаться
до собственного тайм-аута клиента 005; поздний ответ игнорируется и не запускает команду.

## Ручной прогон Алексея и исправления интерфейса

Источник — сообщение Алексея и три скриншота после запуска подготовленного
Mac-сценария. По переданному выводу разрешённая попытка
9688242d-8954-44ac-8b13-840a650ccbd5 вернула completed, exitCode=0,
stdout=guard-check, пустой stderr, без усечения. Во второй попытке выбран
отказ; на скриншоте status=not_executed, code=DENIED. Время и отдельные
показатели LLM этим выводом не измерялись.

Обнаружено и исправлено:

- UI-001: не виден итог быстрой команды. Добавлены цветные статусы и понятные
  результат, код завершения, stdout/stderr. Сырой JSON — только в раскрываемых
  технических данных; последний известный результат не стирается при обрыве.
- UI-002: guard:check закрывал Client сразу после ответа. Теперь соединение
  сохраняется до q/Ctrl+C; Enter повторяет безопасный запрос через ту же сессию.
- UI-003: Markdown показывался как текст. Ограниченный renderer создаёт DOM-узлы
  strong/code/list/text, а не вставляет непроверенный HTML. HTML, изображения
  и обработчики событий из объяснения не выполняются.
- UX-004: переход в браузер неудобен. Подготовлено собственное расширение
  Agent Guard для desktop VS Code. Это не встраивание в чат Codex/GigaCode.

Итоговая серия после изменений: **202/202 теста**, включая сохранение одной
MCP-сессии через отказ/разрешение, DOM-состояния, безопасный Markdown, потерю
связи и активацию собранного расширения с mock VS Code host. Сборка и проверка
типов проходят. Состав VSIX проверен: manifest, README, один bundled CJS entry;
ключи, конфигурации пользователя и node_modules в него не включены.
На момент этой серии нативная IDE/Windows не проверялись. Позднее Алексей сообщил
об успешной ручной проверке панели VS Code. Старые 192 проверки выше остаются историей.

## Установка панели VS Code

Из корня репозитория после npm ci --ignore-scripts:

```sh
npm run vscode:package
code --install-extension artifacts/agent-guard-panel-0.0.2.vsix
```

Если code не доступен в PATH: Extensions → меню ⋯ → Install from VSIX…,
выбрать файл artifacts/agent-guard-panel-0.0.2.vsix. Если VS Code предложит
перезагрузить окно, выполнить Reload Window. Расширение устанавливает пользователь;
агент его автоматически не устанавливает и в Marketplace не публикует.

Открыть доверенную локальную папку и запустить guard:check с конфигурацией как
выше. При новом ожидающем решении панель появится рядом с редактором, сохраняя
фокус. Вручную открыть: Command Palette → Agent Guard: открыть панель.
Кнопка Guard также есть в строке состояния. Если MCP-серверов несколько,
использовать Agent Guard: выбрать сервер; выбранный PID должен соответствовать
нужной рабочей папке. Публичных команд «автоматически разрешить» нет.

Проверить в реальном VS Code: объяснение с форматированием, цвета ожидания/
исполнения/успеха/отказа, сохранение последнего результата, Enter для повторного
вызова без закрытия панели, q для остановки. Закрытие панели во время ожидания
отменяет попытку. Браузер одновременно не открывать: закрытие одного из UI
может отменить текущую попытку. Автооткрытие можно отключить agentGuard.autoOpen.

Секрет читает extension host из служебного каталога, он не передаётся в Webview.
Webview не выполняет прямые сетевые запросы: только ограниченный message bridge
state/decision/cancel. Проверены привязка к loopback и запрет произвольных методов.
Расширение не запускает MCP-сервер само: его запускает клиент проверки или агент.
Если AGENT_GUARD_STATE_DIR изменён, расширение должно работать с тем же каталогом;
для первого ручного прогона использовать стандартный каталог пользователя.

Поддерживаются как цель локальные macOS/Windows desktop VS Code. SSH, WSL,
Dev Containers и браузерный vscode.dev пока не включены. Собственная панель
не доказывает интеграцию или запрет обходных инструментов Codex/GigaCode.
Полное меню политик/LLM и системное хранилище ключей ещё относятся к 004.
